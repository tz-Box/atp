> **学习目标**：为一个平台从没见过的算法类型，从零定义出完整的评测能力——数据格式、世界、判据。

## 4.0 你真的需要写插件吗

先做这个判断，三个问题全是"是"就别写，回[第 3 关](03-第3关-定义benchmark.md)：

```
① 现有 schema 能表达你的观测和输出吗？
   （查 plugins/*/contract.md §1）
              │
   否 ────────┴──────── 是
   │                     │
   ▼                     ▼
 写插件      ② 现有 World 能产生你要的工况吗？
             （现有：ctrl.invp.sim / nav2d.sim / manip.force.sim
               / pipe.slam.synthetic / .rosbag / .rostopic / .device）
                        │
             否 ────────┴──────── 是
             │                     │
             ▼                     ▼
           写插件      ③ 现有 checker 能表达你的及格标准吗？
                                  │
                       否 ────────┴──────── 是
                       │                     │
                       ▼                     ▼
                     写插件            不用写，配场景就够了
```

常见的中间情况：**只有 ③ 是"否"**（数据格式和世界都能复用，只是判分方式不同）。这时候你只需要给现有插件**加一个 checker**，不用新建整个插件包——`pipe.slam` 就同时注册了 `pipe.slam.ape` 和 `pipe.slam.pipe` 两个判据。

### 插件住在哪：一件需要提前说清的事

**插件在 ATP 仓的 `plugins/` 目录下，不在你的算法仓里。**

框架加载插件的方式是按命名空间在 ATP 仓的 `plugins/<命名空间>/` 找 `__init__.py`（见 `src/autotest/registry.py` 的 `load_plugin`）。所以：

> **新增一个插件 = 给 ATP 仓提一个 PR。**

这不是工程上的偷懒，是刻意的治理设计：

| 如果插件放在算法仓 | 后果 |
|---|---|
| 每个算法仓一份判据 | 两个 SLAM 算法用不同的 ATE 定义，**分数不可比** |
| 算法作者能改判据 | 测不过就放宽阈值，[导读](00-导读与学习路径.md) §4 的黄金纪律失效 |
| 数据格式各自定义 | 换个算法就要重新对接数据源，三源透明没了 |

放在 ATP 仓意味着插件是**公共资产**：有唯一版本、有 `contract.md` 作为对外契约、改动要评审、所有同类算法共用同一把尺子。

**分工建议**（现实中要两个角色坐下来谈）：

| 插件的哪一部分 | 谁主导 | 因为 |
|---|---|---|
| `data.py` 观测/输出 schema | **算法工程师**主导 | 只有他知道算法真正需要什么输入、能产出什么 |
| `sim.py` / `dataset.py` 世界 | **仿真/测试工程师**主导，算法工程师复核物理合理性 | 世界的保真度决定测试结论有没有意义 |
| `checker.py` 判据与指标 | **测试工程师**主导 | 判据必须独立于任何一个算法实现 |
| `contract.md` | **共同签字** | 这是双方的接口约定 |

## 4.1 插件是什么：一门"考试科目"的完整定义

```
plugins/<命名空间>/          # 命名空间即目录名，如 ctrl.invp / pipe.slam / nav2d
├── contract.md             # 考纲（给人读的对外契约）
├── data.py                 # 卷面格式：观测长什么样、答案长什么样
├── sim.py                  # 出题的机器 —— 闭环仿真世界
│   或 dataset.py           #   或题库 —— 开环数据集回放
├── checker.py              # 评分标准
├── __init__.py             # 注册：把上面三件挂进平台注册表
├── scenarios/*.yaml        # 样卷（预置场景，供算法仓抄）
└── proto/*.proto           # 可选：跨语言 schema（C++ 算法接入前才需要）
```

对照[导读](00-导读与学习路径.md)的四个问题：**插件回答 Q2（怎么考）和 Q4 的实现部分（用什么指标判）**；算法仓回答 Q1（考谁）和 Q3（考哪些工况）。

真实规模参考：`ctrl.invp` 全套约 **250 行 Python**。插件不是大工程，难的是**设计决策**，不是代码量。

## 4.2 三条注册线与归属校验

插件通过三个注册函数把自己挂进平台。**注册键一律带命名空间**，裸名会被拒绝。

| 注册函数 | 注册什么 | 键的样子 | 谁来消费 |
|---|---|---|---|
| `register_data(kind, schema_id, decoder, encoder)` | 数据格式的编解码器 | `ctrl.invp.InvpObs` | 世界、算法、判据三方 |
| `register_dataset(key, factory)` | 数据源工厂（返回一个 `IWorld`） | `ctrl.invp.sim` | 场景文件的 `dataset.type` |
| `register_checker(key, cls)` | 判据类 | `ctrl.invp.upright` | 场景文件的 `checker` |

**归属校验**——框架靠这条规则确保三方配套，装配期 fail fast：

```
        数据源  produces = ["ctrl.invp.InvpObs"]
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
   判据 consumes           算法 manifest consumes
   ["ctrl.invp.InvpObs"]   ["ctrl.invp.InvpObs"]

        校验：produces ⊇ consumes，否则拒绝装配
```

框架核心**完全不认识**"倒立摆"或"SLAM"——它只做集合包含判断。这就是[契约](scheme/途零-AutotestService接口契约v1.2.md) §1 那条"核心只处理交互逻辑，不处理数据本身"的落地方式，也是为什么**新增一类算法测试 = 新增一个插件包，核心代码零改动**。

### 第 1 步：先写 `contract.md`，不是先写代码

**这一步决定了插件的成败，值得花掉总时间的三分之一。**

要回答的五个问题：

| # | 问题 | 倒立摆的答案 |
|---|---|---|
| 1 | 算法每帧**看到**什么？ | `x, x_dot, theta, theta_dot`（SI 单位，θ=0 竖直向上） |
| 2 | 算法每帧**回**什么？ | `force`（作用于小车的水平力，N） |
| 3 | 判据需要什么**真值**？ | 任务参数：`dt, max_steps, theta_limit, x_limit` |
| 4 | **指标**是什么，及格线怎么表达？ | `survived` + `settle_error ≤ settle_threshold` |
| 5 | 需要什么**本体**？ | 纯仿真台架 `invp_sim`，无传感器 |

问题 1 和 2 是**抽象层级的选择**，是整个插件里最需要想清楚的决策。以倒立摆为例：

> **为什么观测是 `(x, ẋ, θ, θ̇)` 四个数，而不是一张摄像头图像？**
> 因为这个科目考的是**控制律**，不是状态估计。如果观测给图像，那么算法挂了你分不清是"控制律不行"还是"视觉估计不准"——**一次测试只该有一个变量**。
> 如果你真的要考"从图像直接出控制量"的端到端算法，那是**另一个科目**，应该是另一个插件（另一套 schema、另一个世界、可能还有另一套指标）。
>
> **为什么指令是力 `F`，而不是电机电压或 PWM？**
> 力是这个物理问题的自然接口。给电压就把电机模型的责任推给了算法，而电机模型是本体特性，不该由控制算法承担。
>
> **通用原则：schema 的抽象层级 = 你想考察的那一层的输入输出，上下游都要挡在外面。**

问题 3 也有个陷阱：**GT 里绝不能出现"答案"**。倒立摆的 GT 是 `{dt, max_steps, theta_limit, x_limit}`——是**任务参数**，不是"正确的力序列"。判据拿它来知道"撑满是多少步、什么算倒"，而不是拿来比对标准答案。（对 SLAM 这种估计类任务，GT 确实是真值轨迹，但它只交给判据，**永远不进算法的观测**。）

`contract.md` 的必备要素（[契约](scheme/途零-AutotestService接口契约v1.2.md) §7.3）：
① schema 字段级定义（含版本 `v`）；② 指标定义与默认阈值；③ 数据源清单与各 config 字段；④ `required_sensors` 与本体要求；⑤ 预置场景说明；⑥ 版本与变更记录。

参考成品：[`plugins/ctrl.invp/contract.md`](../plugins/ctrl.invp/contract.md)（一页纸）。

### 第 2 步：`data.py` —— 定义卷面

```python
"""ctrl.invp 数据 schema：倒立摆观测 payload（InvpObs）与闭环指令（InvpAction）。"""
from dataclasses import dataclass
import msgpack
from autotest.protocol.schema import register_data


@dataclass
class InvpAction:
    """闭环指令：作用于小车的水平力（N），仿真侧按 force_limit 截断。"""
    force: float

    def to_dict(self) -> dict:
        return {"force": self.force}

    @classmethod
    def from_dict(cls, data: dict) -> "InvpAction":
        return cls(force=float(data["force"]))


@dataclass
class InvpObs:
    """观测 payload：小车位置/速度 + 摆杆角度/角速度（SI 单位，theta=0 为竖直向上）。"""
    x: float
    x_dot: float
    theta: float
    theta_dot: float

    def to_dict(self) -> dict:
        return {"x": self.x, "x_dot": self.x_dot,
                "theta": self.theta, "theta_dot": self.theta_dot}

    @classmethod
    def from_dict(cls, data: dict) -> "InvpObs":
        return cls(x=float(data["x"]), x_dot=float(data["x_dot"]),
                   theta=float(data["theta"]), theta_dot=float(data["theta_dot"]))


def register_schemas():
    """注册跨进程数据 schema（observation/action）。

    GT（ctrl.invp.InvpTask）不注册：进程内传递、不编码。
    """
    register_data("observation", "ctrl.invp.InvpObs",
                  lambda b: InvpObs.from_dict(msgpack.unpackb(b, raw=False)),
                  lambda obj: msgpack.packb(obj.to_dict(), use_bin_type=True))
    register_data("action", "ctrl.invp.InvpAction",
                  lambda b: InvpAction.from_dict(msgpack.unpackb(b, raw=False)),
                  lambda obj: msgpack.packb(obj.to_dict(), use_bin_type=True))
```

**要点：**

- **dataclass 就是 schema 的唯一事实源**——"代码即契约"。`contract.md` 描述它，但字段以代码为准。
- `register_data(kind, schema_id, decoder, encoder)`：`kind` 是 `observation` / `result` / `action` 三选一。**同一个 schema_id 在不同 kind 下是不同的键**。
- **为什么 GT 不注册**：GT 从世界直接交给判据，两者在同一个进程里，不需要序列化。它走另一套更轻的信封：`{schema, v, data}`（`encode_ground_truth`），`data` 是原样的 dict。

**跨进程传的到底是什么**——数据面信封（[契约](scheme/途零-AutotestService接口契约v1.2.md) §4.2）：

```python
{"schema": "ctrl.invp.InvpObs",   # 命名空间.类型名
 "v": 1,                          # schema 版本
 "enc": "msgpack",                # 编码方式
 "blob": b"..."}                  # 序列化后的字节
```

外面还有一层观测外层信封：`{timestamp, module, data}`。**收发双方遇到未知 schema 会拒收并记错误，不会静默透传**——这是设计上有意为之：宁可炸掉，也不要让算法收到一堆解不开的字节还继续跑。

**版本演进规则**（一定要写进 `contract.md`）：

| 改动 | `v` 怎么办 |
|---|---|
| 加字段（消费者可以忽略） | `v` **不变** |
| 改字段语义 / 删字段 | `v + 1`，且**新旧 decoder 同时注册一个过渡周期** |

**二进制字段怎么办**（点云、图像）：msgpack 原生支持 bytes，约定用 `{shape, dtype, data: bytes}` 装 numpy 数组，参考 `plugins/pipe.slam/data.py`。

**关于 C++ 算法**：现阶段默认 `enc=msgpack`，Python dataclass 即事实源。要接原生 C++ 算法（不经 ROS2 bridge）时，该插件必须补 `.proto` 文件并切 `enc=pb`——`.proto` 那时就成为跨语言的事实源。入门阶段不用管。

### 第 3 步：`sim.py` —— 造出题的世界

闭环插件的核心。要实现 `IWorld` 四件事：

```python
class IWorld(ABC):
    realtime: bool = False       # 实时源（真机/ROS topic）为 True，自带节奏
    closed_loop: bool = False    # True = step 消费 action（服务端据此选闭环会话）
    produces: list[str] = []     # 产出的观测 schema，供 produces ⊇ consumes 校验

    def testcases(self) -> list[str]: ...
    def reset(self, testcase_id) -> dict: ...                     # → 首帧观测信封
    def step(self, action=None) -> tuple[dict|None, bool, dict]: ...  # → (观测, done, info)
    def get_ground_truth(self) -> dict: ...                       # → GT 信封
    def close(self) -> None: ...
```

倒立摆的实现（节选真实代码）：

```python
class InvpSimWorld(IWorld):
    closed_loop = True                          # ①
    produces = ["ctrl.invp.InvpObs"]            # ②

    @classmethod
    def from_config(cls, cfg: dict) -> "InvpSimWorld":          # ③
        """场景 config → World：{testcases: {id: {theta0, ...}}, physics: {...}}。"""
        raw = cfg.get("testcases")
        if not raw:
            raise ValueError("ctrl.invp.sim 的 dataset.config 缺 testcases")
        scenarios = {tid: InvpScenario(**params) for tid, params in raw.items()}
        physics = InvpPhysics(**cfg["physics"]) if cfg.get("physics") else None
        return cls(scenarios, physics)

    @property
    def testcases(self) -> list[str]:
        return list(self._scenarios)

    def reset(self, testcase_id: str) -> dict:                   # ④
        self._scenario = self._scenarios[testcase_id]
        self._x, self._x_dot = self._scenario.x0, self._scenario.x_dot0
        self._theta, self._theta_dot = self._scenario.theta0, self._scenario.theta_dot0
        self._time = 0.0
        self._steps = 0
        return self._observation()

    def step(self, action: dict) -> tuple[Optional[dict], bool, dict]:   # ⑤
        invp_action = decode_action(action["data"])                      # ⑤a
        p = self._physics
        force = max(-p.force_limit, min(p.force_limit, invp_action.force))  # ⑤b 截断

        # ⑤c 车-摆动力学（Sutton-Barto 参数化，半隐式欧拉）
        total_mass = p.cart_mass + p.pole_mass
        polemass_length = p.pole_mass * p.half_length
        costheta, sintheta = math.cos(self._theta), math.sin(self._theta)
        temp = (force + polemass_length * self._theta_dot**2 * sintheta) / total_mass
        theta_acc = (p.g * sintheta - costheta * temp) / (
            p.half_length * (4.0 / 3.0 - p.pole_mass * costheta**2 / total_mass))
        x_acc = temp - polemass_length * theta_acc * costheta / total_mass

        dt = self._scenario.dt
        self._x_dot += x_acc * dt;          self._x += self._x_dot * dt
        self._theta_dot += theta_acc * dt;  self._theta += self._theta_dot * dt
        self._time += dt
        self._steps += 1

        if abs(self._theta) > p.theta_limit:                             # ⑤d 终止条件
            return self._observation(), True, {"reason": "fell"}
        if abs(self._x) > p.x_limit:
            return self._observation(), True, {"reason": "out_of_bounds"}
        if self._steps >= self._scenario.max_steps:
            return self._observation(), True, {"reason": "survived"}
        return self._observation(), False, {"reason": None}

    def get_ground_truth(self) -> dict:                                  # ⑥
        p = self._physics
        return encode_ground_truth("ctrl.invp.InvpTask", {
            "dt": self._scenario.dt, "max_steps": self._scenario.max_steps,
            "theta_limit": p.theta_limit, "x_limit": p.x_limit,
        })

    def _observation(self) -> dict:                                      # ⑦
        return make_observation("ctrl.invp", self._time, encode_observation(
            "ctrl.invp.InvpObs",
            InvpObs(x=self._x, x_dot=self._x_dot,
                    theta=self._theta, theta_dot=self._theta_dot)))
```

**逐条看设计要点：**

**① `closed_loop = True`** —— 服务端就靠这个标记决定走闭环会话还是开环推流。写错了整个流程就跑偏。

**② `produces`** —— §4.2 那条归属校验的左半边。

**③ `from_config`：这是测试工程师的配置面** —— 它定义了场景文件的 `dataset.config` 能写什么。设计它就是在设计"测试工程师有多大自由度"：

```yaml
dataset:
  type: ctrl.invp.sim
  config:
    testcases:                        # ← 从这里长出来的
      small_push: { theta0: 0.05 }
    physics:                          # ← 和这里
      { g: 9.8, cart_mass: 1.0, ... }
```

**把握原则**：**工况参数**（初始状态、扰动、时长）必须可配——不然测试工程师加不了新工况；**物理常数**可配但要有合理默认；**算法能力相关的东西**（比如"允许多大的力"）要想清楚——`force_limit` 放在 physics 里意味着它是**世界的约束**（执行器上限），而不是算法的选择，这是对的。

注意 `from_config` **缺 `testcases` 直接抛异常**，不给默认值。这是有意的：让测试工程师显式声明考什么，而不是悄悄用一套隐藏的默认工况。

**④ `reset`：把世界恢复到 testcase 的初始状态**，返回首帧观测。注意 `self._time = 0.0`——**每个 testcase 的时钟从 0 开始**。

**⑤ `step`：一次交互的全部**

- **⑤a** action 进来是 payload dict（`{module, data}`），用 `decode_action` 解出对象。
- **⑤b 截断**：物理约束在世界里执行，不指望算法自觉。**凡是本体的物理限制，都该由世界强制，不该写进判据，更不该指望算法遵守。**
- **⑤c** 积分一步。
- **⑤d 终止条件三态**——这里有个关键设计点：

> **终止条件本身就是一种隐式判据。** `fell` / `out_of_bounds` / `survived` 这三个状态，直接决定了判据能看到多长的轨迹。所以**终止条件必须和判据对齐**：世界判"倒了"用 `theta_limit`，判据也从 GT 里读同一个 `theta_limit`（见第 4 步），两边永远不会打架。
>
> 反面做法：世界里写死 `0.2095`，判据里也写死 `0.21`——某天有人改了一个，测试就开始给出无法解释的结果。

**⑥ `get_ground_truth`：把任务参数交给判据**，而不是"标准答案"。GT 用 `encode_ground_truth`（不编码，进程内传 dict）。

**⑦ `_observation`：组外层信封**。`make_observation(命名空间, 时间戳, 数据面信封)`。**时间戳取仿真时钟**（reset=0，每步 +dt）——这是全链路的唯一权威时间，算法拿到的就是它。

**⑧ 一条不在代码里但极其重要的纪律：确定性。**

> **世界必须是确定性的：同样的 testcase + 同样的 action 序列，必须产生完全相同的观测序列。**
> 一旦引入未播种的随机（传感器噪声、随机初值、多线程调度顺序），基线回归立刻失去意义——你分不清指标波动是算法改了还是运气变了。
> 需要噪声？**用固定种子**，并把种子作为 testcase 参数暴露出去（这样"不同种子"本身就成了一组工况）。

### 开环插件的对照：`dataset.py`

开环不需要实现完整 `IWorld`，只要实现一个更简单的 **Dataset 协议**，框架用 `DatasetWorld` 包一层：

```python
class Dataset(Protocol):
    testcases: list[str]
    produces: list[str]

    def frames(self, testcase_id: str) -> Iterator[dict]:
        """逐帧产出 observation 外层信封（生成器，可以边读边喂，不必全部载入内存）。"""

    def ground_truth(self, testcase_id: str) -> dict:
        """返回 GT 信封。"""
```

**两种世界的对照表：**

| | 闭环 `sim.py` | 开环 `dataset.py` |
|---|---|---|
| 实现 | 完整 `IWorld` | `Dataset` 协议（3 个成员），框架包 `DatasetWorld` |
| `step` 收 action | ✅ | ❌（忽略，按序返回下一帧） |
| `done` 由什么决定 | 终止条件（摔倒/越界/超时） | 数据耗尽 |
| 一个 testcase 是 | 初始状态 + 动力学 | 一段录好的帧序列 |
| 判据收到的 records | **观测轨迹** | **算法的 result 序列** |
| 确定性来自 | 积分确定 + 无随机 | 数据不变 |

### 第三种形态：实时流 / 真机

`StreamWorld`（帧缓冲 + `idle_timeout`）及其子类 `RostopicWorld` / `DeviceWorld` 让同一个插件能直接接 ROS topic 或真实设备。它们的 `realtime = True`，自带节奏（`clock_rate` 对它们不生效）。

**这正是"三源透明"的兑现处**：同一份算法、同一个判据、同一套 schema，`dataset.type` 从 `pipe.slam.rosbag` 换成 `pipe.slam.device`，就从"回放数据集"变成了"接真机"，**算法代码一行不改**。设计 schema 时把这一点放在心上——**别让 schema 里出现只有仿真才有的字段**（比如"真实位姿"），否则真机那条路就走不通了。

### 第 4 步：`checker.py` —— 写评分标准

```python
class InvpChecker(IChecker):
    """records 为 observation 外层信封列表（首帧为 RESET 观测，其后每 action 一步）。

    passed = 撑满 max_steps（survived）且末段 10% 平均 |theta| ≤ settle_threshold。
    """

    name = "ctrl.invp.upright"
    consumes = ["ctrl.invp.InvpObs"]                      # ①

    def evaluate(self, records, ground_truth, config=None) -> Score:
        cfg = config or {}
        gt_data = decode_ground_truth(ground_truth)       # ②
        max_steps = int(gt_data.get("max_steps", 0))
        dt = float(gt_data.get("dt", 0.02))
        theta_limit = float(gt_data.get("theta_limit", 0.2095))
        settle_threshold = float(cfg.get("settle_threshold", 0.02))   # ③

        thetas = self._thetas(records)                    # ④
        if max_steps <= 0 or not thetas:
            return Score(metrics={}, passed=False)        # ⑤ 拿不到数据 = 不过

        executed = len(thetas) - 1                        # ⑥ 首帧是 reset 观测，不计执行步数
        survived = executed >= max_steps
        tail = thetas[-max(1, len(thetas) // 10):]        # 末段 10%
        settle_error = sum(abs(t) for t in tail) / len(tail)
        max_abs_theta = max(abs(t) for t in thetas)
        upright = sum(1 for t in thetas if abs(t) <= theta_limit) / len(thetas)

        passed = survived and settle_error <= settle_threshold        # ⑦
        return Score(                                                 # ⑧
            metrics={
                "survived": 1.0 if survived else 0.0,
                "survival_time": round(executed * dt, 4),
                "max_abs_theta": round(max_abs_theta, 6),
                "settle_error": round(settle_error, 6),
                "upright_ratio": round(upright, 4),
            },
            passed=passed,
        )

    @staticmethod
    def _thetas(records) -> list[float]:                  # ④
        thetas = []
        for rec in records:
            if not isinstance(rec, dict) or \
               rec.get("data", {}).get("schema") != "ctrl.invp.InvpObs":
                continue                                  # ← 按 schema 过滤，不认识的跳过
            thetas.append(decode_observation(rec["data"]).theta)
        return thetas
```

**逐条看：**

**① `consumes`** —— 归属校验的右半边。

**② 从 GT 拿任务参数，而不是硬编码** —— 呼应第 3 步 ⑤d 的对齐纪律。世界改了 `max_steps`，判据自动跟随。

**③ 阈值从 `config` 取，并给默认值** —— `config` 就是场景文件的 `checker_config`。**所有可能需要按场景调整的数值，都必须走 config；写死在判据里的数值，测试工程师永远改不到。**

**④ ⚠ `records` 的形态是最大的坑：**

| 模式 | `records` 是什么 | 怎么解 |
|---|---|---|
| **闭环** | **observation 外层信封列表** `{timestamp, module, data}`，第一条是 RESET 首帧观测 | `decode_observation(rec["data"])` |
| **开环** | **result payload 列表** `{module, data}` | `decode_result(rec["data"])` |

两种都要**先按 `rec["data"]["schema"]` 过滤**再解码——一个 testcase 里可能混有多种 schema 的记录，不认识的必须跳过而不是崩掉。开环的写法见 [`plugins/pipe.slam/checker.py`](../plugins/pipe.slam/checker.py) 的 `_decode_results`。

**⑤ 数据不足要明确判不过**，不要抛异常也不要给个假分数。

**⑥ 首帧不算执行步数** —— 这类边界处理必须写进 `contract.md`，否则下一个读代码的人算不明白为什么 `n_records` 是 501 而不是 500。

**⑦ `passed` 表达式尽可能短** —— 这里只有两项。一次红能被一句话解释清楚，才有人愿意去修。

**⑧ `Score(metrics, passed)`** —— `metrics` 必须是 `dict[str, float]`（会进报告、进基线对比，所以只能是数值）。

**判据设计的四条守则：**

1. **`passed` 单一明确，`metrics` 尽量丰富**（第 3 关 §3.4）。
2. **指标尽量做成"越小越好"** —— 基线回归对比是这么假设的（第 3 关 §3.4 的机制提醒）。设计新判据时这是免费就能做对的事：用 `settle_error` 而不是 `stability_score`。
3. **判据不许"帮算法找补"** —— 不要写"如果结果为空就用上一帧的值"、"角度超限但只超了一点点就放过"这种逻辑。判据发现不了问题，测试就白做了。
4. **判据不许知道被测的是谁** —— 判据里不能出现任何算法名，更不能有 `if algo_version == ...`。

## 4.4 本体资产 `body`：为什么纯仿真也要声明

`body/*.yaml` 描述"这台机器人是什么、传感器装在哪"：

```yaml
# body/invp_sim.yaml —— 纯仿真控制台架
body:
  name: invp_sim
  version: "1"
  urdf_path: ""
  sensors: {}        # 无机器人传感器，sensor_config 为空
```

有传感器的本体长这样（[`body/pbox_v1.yaml`](../body/pbox_v1.yaml) 节选，**这是仓里的真实内容**）：

```yaml
body:
  name: pbox
  version: 1
  urdf_path: body/pbox_v1.urdf
  sensors:
    lidar:
      front:
        topic: /rslidar_points_front   # ★必填：框架据此生成 INIT 下发的 sensor_config
        type: pointcloud2
        extrinsics:
          xyz: [0.30, 0.0, 0.25]       # 相对 base_link，米
          rpy: [0.0, 0.0, 0.0]         # roll pitch yaw，弧度
      rear:
        topic: /rslidar_points_rear
        type: pointcloud2
        extrinsics: { xyz: [-0.30, 0.0, 0.25], rpy: [0.0, 0.0, 3.14159] }   # 朝后装
    imu:
      imu: { topic: /IMU, type: imu, extrinsics: {...} }
```

> ⚠ `topic` 是**硬性必填**——`body.py` 的 `sensor_topics` 直接取 `info["topic"]` 生成
> INIT 下发的 `sensor_config`，缺了会 KeyError。`type` / `extrinsics` 供 World 与
> converter 消费（按外参做坐标变换、按规格校验数据维度）。

**看得见的效果**：`cicd_test_slam` 的 SUT 声明 `required_sensors = {"lidar": ["front"]}`，
握手时框架拿它和 `pbox_v1` 派生出的 `sensor_config` 比对——实例名 `front` 存在，校验通过；
写成 `left` 就会 fail fast 并列出可用实例。这就是 body 在评测里的实际作用：
**让"算法需要什么传感器"和"这台机器人有什么传感器"能被机械核对，而不是靠人记。**

**为什么本体要独立于插件**：多个算法（SLAM、导航、检测）跑在**同一台机器人**上，共享同一套传感器布置与外参。把它做成独立资产，改一次外参所有插件都跟着对。而且数据集常常缺标定，本体提供了权威的预定义值。

**它怎么串起来**（三处名字必须对齐，否则装配期 fail fast）：

```
body/xxx.yaml 的 sensors 实例名
        │
        ├─→ 场景文件 sensor_config 覆盖（可选）
        │        └─→ 经 INIT 下发给算法（第 2 关 §2.4 的 config["sensor_config"]）
        └─→ 算法 manifest 的 required_sensors 必须被它覆盖
```

**什么时候要新建 body**：新机型、新传感器布置。纯仿真台架照抄 `invp_sim` 改个名字就行。**改动现有 body 要谨慎**——所有引用它的场景都会受影响。

## 4.6 反模式清单

写完对照检查一遍：

| ❌ 反模式 | 为什么错 |
|---|---|
| 判据里出现某个算法的名字或版本判断 | 判据必须独立于被测对象 |
| 阈值写死在 `checker.py`，不走 `checker_config` | 测试工程师改不到，benchmark 分不了级 |
| schema 里塞进真值字段（"顺便把 GT 也发给算法"） | **等于开卷考试**，测出来的分数无意义 |
| 世界用了未播种的随机 | 基线回归失效，指标波动无法归因 |
| 指标方向混乱（有的越大越好有的越小越好） | 回归对比退化成 `same`（第 3 关 §3.4） |
| 终止条件和判据用了两套常数 | 早晚会不一致，给出无法解释的结果 |
| 世界不做物理约束，指望算法自觉 | 算法一个 bug 就能给出 10^6 N 的力，测试结论失去意义 |
| 插件 import 了某个具体算法 | 插件是公共资产，不能依赖任何一个算法仓 |
| schema 抽象层级横跨多层（图像进、力矩出） | 一次测试考了两件事，挂了分不清是谁的锅 |
| 没有 `contract.md`，或它和代码不一致 | 插件是对外契约，没有契约就没有插件 |
