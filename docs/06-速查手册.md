## 1. 术语表

| 术语 | 一句话 | 住在哪 | 哪一关讲的 |
|---|---|---|---|
| **SUT** | System Under Test，被测算法进程（黑盒） | 你的算法仓 | [2](02-第2关-接入你的算法.md) |
| **manifest** | 算法仓**根目录**的 `scenario.yaml`：怎么启动我、我吃什么、有哪几套题 | 你的算法仓根 | [2](02-第2关-接入你的算法.md) §2.6 |
| **场景文件** | `scenarios/*.yaml`：一次评测跑什么数据、用什么判定 | 你的算法仓 | [3](03-第3关-定义benchmark.md) §3.2 |
| **场景清单** | manifest 里的 `scenarios:` 列表，每项一个 `id`（Hub 勾选的就是它） | 你的算法仓根 | [3](03-第3关-定义benchmark.md) §3.5 |
| **testcase** | 一个具体工况（一段数据 / 一组初始状态） | 场景文件的 `dataset.config` | [3](03-第3关-定义benchmark.md) §3.3 |
| **插件 plugin** | 一门"考试科目"的完整定义：schema + 世界 + 判据 | **ATP 仓** `plugins/<命名空间>/` | [4](04-第4关-开发评测插件.md) |
| **命名空间** | 插件的目录名 = 所有注册键的前缀，如 `ctrl.invp` | ATP 仓 | [4](04-第4关-开发评测插件.md) §4.2 |
| **World** | 数据源抽象：仿真 / 数据集回放 / 真机实时，三形态同一接口 | 插件的 `sim.py` / `dataset.py` | [4](04-第4关-开发评测插件.md) §4.3 |
| **Checker 判据** | 拿轨迹和真值算指标、判过没过 | 插件的 `checker.py` | [4](04-第4关-开发评测插件.md) §4.3 |
| **GT 真值** | Ground Truth，只交给判据，**永不进算法观测** | World 产出 | [4](04-第4关-开发评测插件.md) §4.3 |
| **body 本体** | 机器人型号 + 传感器布置 + 外参 | ATP 仓 `body/*.yaml` | [4](04-第4关-开发评测插件.md) §4.4 |
| **schema** | 一种数据格式的命名空间键，如 `ctrl.invp.InvpObs` | 插件的 `data.py` | [4](04-第4关-开发评测插件.md) §4.3 |
| **基线 baseline** | 上一次（通常是主干）的评测结果，用于回归对比 | 评测机 `artifacts/baseline.json` | [3](03-第3关-定义benchmark.md) §3.6 |
| **job_id** | 一次评测的编号，`artifacts/<job_id>/` 是它的现场 | 评测机 | [1](01-第1关-跑通第一次评测.md) §1.8 |
| **cid** | `correlation_id`，三平台对账锚点，形如 `chk_01J...` | Hub 生成 | [5](05-第5关-接入CI流水线.md) §5.3 |
| **Hub** | cicd-hub，流水线编排：收 GitHub 事件、调度 ATP、回写 PR | 管理面机器 | [5](05-第5关-接入CI流水线.md) |
| **PMS** | 项目管理系统：任务卡、交付物、飞书通知 | 管理面机器 | [5](05-第5关-接入CI流水线.md) |
| **tzcomm** | 底层通信库（仿 ROS2 API，daemon + Redis 发现层）。SUT 的唯一依赖，**不依赖 ROS2** | 评测机 | —— |

**两个最容易混的**：

- **manifest vs 场景文件**：都叫 `scenario.yaml` 家族，但 manifest 在**仓根**（"这个仓怎么被测"），场景文件在 `scenarios/`（"跑什么数据、什么算过"）。报错信息说 manifest 时，指仓根那个。
- **场景 vs testcase**：一个场景（清单项）里可以有多个 testcase。报告里 `full:medium_push` = 场景 `full` 的 testcase `medium_push`。

## 2. 我要改 X，该动哪个文件

| 我想… | 改哪里 | 谁的活 |
|---|---|---|
| 换算法的推理逻辑 | 你的算法仓：`on_step` | 算法工程师 |
| 换算法启动方式 / 加依赖 | 你的算法仓：manifest 的 `launch` / `runtime` | 算法工程师 |
| 调算法参数（增益、阈值…） | 场景清单项或场景文件的 `hyperparams` | 都可以 |
| **加一个新工况** | 场景文件的 `dataset.config.testcases` | 测试工程师 |
| **改及格线** | 场景文件的 `checker_config` | 测试工程师 |
| 加一级 benchmark（smoke/full/sweep） | manifest 的 `scenarios:` 清单 | 测试工程师 |
| 改评测机上的滚动基线 | `client report --save-baseline` / CI 的 `save_baseline` | 测试工程师 |
| **加一个新指标** | ATP 仓：`plugins/<ns>/checker.py` + `contract.md` | 测试工程师（提 ATP PR） |
| **改仿真物理 / 加终止条件** | ATP 仓：`plugins/<ns>/sim.py` + `contract.md` | 仿真/测试工程师（提 ATP PR） |
| **改观测/输出的数据格式** | ATP 仓：`plugins/<ns>/data.py` + `contract.md`（注意版本规则） | 算法工程师主导（提 ATP PR） |
| 新机型 / 改传感器布置 | ATP 仓：`body/*.yaml` | 评测负责人 |
| 改哪个仓派给哪台评测机 | Hub console「设置 → ATP 池」 | Hub 管理员 |
| 把评测结果关联到任务 | PMS 任务编辑表单「仓库」，或项目后台 repo 区块 | 你 |

## 3. CLI 速查

### 本机通路（client 与 server 必须同机）

```bash
python3 -m autotest.client run <manifest路径> [--scenario <场景文件>] [--clock-rate 1.0] [--json]
python3 -m autotest.client matrix <test_matrix.yaml> [--json]      # 交叉测试矩阵
python3 -m autotest.client report <job_id> [--baseline <路径>] [--save-baseline] [--json]

python3 -m autotest.client pause  <job_id>          # 暂停喂帧（世界冻结，算法安全等待）
python3 -m autotest.client step   <job_id> -n 10    # 暂停中单步放行 N 帧（默认 1）
python3 -m autotest.client resume <job_id>          # 恢复全速
```

`--clock-rate`：`1.0`=按原始帧间隔实时复现（默认）｜`>1` 加速｜`<1` 减速｜`0` 全速（仅冒烟）。实时数据源自带节奏，不受影响。

### HTTP 面（和 Hub 走同一套接口，可跨机）

```bash
python3 -m autotest.client atp login          # 交互式录入地址+令牌，落盘 ~/.config/autotest/client.env (600)
python3 -m autotest.client atp whoami         # 查看当前配置来源 + 掩码令牌 + 探活
python3 -m autotest.client atp logout         # 删除配置
python3 -m autotest.client atp health         # GET /atp/health

python3 -m autotest.client atp submit --repo <owner/repo|本地路径> \
        [--ref <分支>] [--scenario <id|["a","b"]>] [--cid <cid>] \
        [--save-baseline] [--no-wait] [--timeout 1800]
python3 -m autotest.client atp status <job_id>
python3 -m autotest.client atp wait   <job_id> [--timeout 1800]
```

环境变量 `ATP_BASE_URL` / `ATP_SERVICE_TOKEN` **优先于**配置文件（CI 注入用）。
浏览器等价入口：`<ATP地址>/console`（飞书登录；admin 可触发，member 只读）。

### 诊断

```bash
python3 -m autotest.commcheck                  # 通信链路自检，退出码 0/1
TZCOMM_LOG_LEVEL=DEBUG python3 ...             # 打开底层通信诊断日志
systemctl --user status autotest               # 服务状态
journalctl --user -u autotest -f               # 服务日志（含评测/调试命令/通信告警）
curl -s localhost:2335/atp/health              # 探活
```

## 4. 排障归因速查

**第一反射：看 `artifacts/<job_id>/session.log`。** 它按时间顺序告诉你评测走到哪一步、在哪崩的。

| 症状 | 看哪里 | 归因 |
|---|---|---|
| 提交即 400，`code: scenario_unknown` | 报文里带可用清单 | **配置**：场景 id 拼写错，或清单没同步 |
| 提交即 400，`code: manifest_missing/invalid` | 报文指明缺失项 | **配置**：对照[附录 Schema](07-附录-scenario-yaml-schema.md) 修 |
| results 有 `<runtime>` 失败条目 | `session.log` 的 `[runtime]` 段 | **环境**：venv/pip 装依赖失败 |
| results 有 `场景id:<scenario>` 失败条目 | `session.log` 对应场景段 | **该场景**装配/执行异常（其余场景不受影响） |
| SUT 进程没起来 / 收不到 READY | `session.log` 的 launch 报错 | **配置/环境**：manifest 的 `launch`、`PYTHONPATH`、venv |
| 装配期 fail fast | 报错直指缺失项 | **声明不一致**：schema 键 / 传感器实例名 / body 三者对不上 |
| 启动报"未知 schema" | 算法进程日志 | **代码**：忘了 `load_plugin`，或 schema 名写错 |
| `comm_health.warnings` 非空（丢包 > 1%） | 报告的 `comm_health` | **底层通信**：把报告发给通信负责人，不是你的算法问题 |
| 收不到帧 / 卡在 step | `TZCOMM_LOG_LEVEL=DEBUG` 起 SUT | **底层通信**：发现层/话题名 |
| 第 1 个 testcase 过、后面开始崩 | 你的 `on_reset` | **算法**：状态没清干净 |
| 改了 `--clock-rate` 结果就变 | 你的算法代码 | **算法**：读了墙上时钟 |
| 链路正常但 metrics 不对 | 判据的 metrics 与 GT | **算法本身** |
| 每次跑结果都不一样 | 世界的随机源 | **插件**：随机没播种（[第 4 关](04-第4关-开发评测插件.md) §4.3 ⑧） |

## 5. 错误码（`POST /atp/evaluations` 的 4xx）

响应统一为 `{"ok": false, "error": "<人类可读>", "code": "<机读>"}`。Hub 收到直接判 failure，不重投。

| code | 触发 |
|---|---|
| `manifest_missing` | 仓里找不到 manifest（指定路径和仓根 `scenario.yaml` 都不存在） |
| `manifest_invalid` | 解析/校验失败：缺 `launch`、清单项缺 `id`/`scenario`、`id` 非法或重复、`runtime.type` 未知 |
| `scenario_unknown` | 引用的场景 id 不在清单中（报文带可用清单） |

另：token 错误 → 401；ATP 未配置 `ATP_SERVICE_TOKEN` 时 `/atp/*` 端点返回 503。

## 6. 协议消息速查

信封：`{"type": str, "session_id": str, "payload": dict, "seq": int|None}`

| type | 方向 | 通道 | payload | 响应 |
|---|---|---|---|---|
| `init` | 服务→算法 | ctl（服务，一问一答） | `{sensor_config, hyperparams, body_profile?}` | `ready` |
| `ready` | 算法→服务 | ctl 响应 | `{module, version, required_sensors}` | — |
| `reset` | 服务→算法 | ctl | `{testcase_id}` | `reset_ack{ok}` |
| `step` | 服务→算法 | obs（topic，不回确认） | `{done, observation}` | 异步 `result`/`action` |
| `result` / `action` | 算法→服务 | result / action | `{module, data}` | — |
| `terminate` | 服务→算法 | ctl | `{reason}` | `final{自统计}` |

**数据面信封**：`{schema, v, enc, blob}`｜**观测外层**：`{timestamp, module, data}`｜**GT 信封**：`{schema, v, data}`（进程内不编码）。

`seq` 是服务端推流帧序号（0 起），排查丢帧用，算法可以忽略。

## 8. 目录地图

### ATP 仓（本仓）

```
src/autotest/          框架核心（无任何算法知识）
  protocol/            消息信封、schema 注册与编解码、话题命名
  world/               IWorld 抽象：回放 / 实时流 / 设备 / 时间戳对齐
  eval/                Runner（开环）、ClosedLoopSession（闭环）、IChecker、Loader、暂停单步
  server/              常驻服务：job 池、留痕、HTTP 面(:2335)、console、docs 门户
  client/              CLI：run/matrix/report/pause/step/resume + atp 子命令
  sdk/                 SutBase（算法侧基类）
  registry.py          插件注册表 + load_plugin
plugins/<命名空间>/     插件包（评测能力，见第 4 关）
body/*.yaml            本体资产
examples/              参考 SUT、manifest 模板、GHA 自测备选
tests/unit|functional/ 测试
artifacts/<job_id>/    评测现场：report.json + session.log；baseline.json 为滚动基线
docs/                  本教程 + scheme/（三平台契约）
deploy/autotest.service systemd 单元（部署说明在文件头注释）
```

### 你的算法仓

```
scenario.yaml          manifest：launch + consumes + 场景清单 + runtime
scenarios/*.yaml       场景文件：body + dataset + checker + 阈值
<你的算法代码>          实现 4 个钩子的进程
requirements.txt       runtime.type=venv 时需要（⚠ 不要写 autotest/tzcomm）
.gitignore             加上 .atp-venv/
```
