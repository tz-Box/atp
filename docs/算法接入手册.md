# 算法接入手册

> 读者：算法工程师。目标：回答一个问题——**"我要在 ATP 平台上测试自己的算法，需要定义哪些东西？"**
>
> 零基础请先看 [快速上手](快速上手.md)（30 分钟跑通）；写 manifest/场景配置时查
> [scenario.yaml Schema](scenario-schema.md)（权威字段表）；接 Hub 自动触发看 [CI 集成](CI集成.md)。

---

## 1. 一张图看懂

```
                        ┌──────────────────────── 定义链（谁定义什么）────────────────────────┐
                        │                                                                  │
 body.yaml ──▶ plugin 包 ──▶ 场景文件 ──▶ scenario.yaml(manifest) ──▶ SUT(你的算法进程) ──▶ CI
 (本体资产)   (plugins/<ns>)  (scenarios/*.yaml)  (算法仓库根)          (4 个钩子)          (Hub 触发)
 机器人型号    数据 schema      选数据集+checker    launch+consumes      协议收发            场景勾选+回调
 传感器布置    +checker+数据源  +传感器+超参        +scenarios 清单+runtime
                        │                                                                  │
                        └──────────────────────────────────────────────────────────────────┘

 运行期：ATP 服务（常驻）读 manifest → 按场景清单装配（校验 produces⊇consumes、body 对齐）
        → 拉起你的 SUT 进程（注入 AUTOTEST_SESSION / AUTOTEST_TOPICS）
        → World 喂帧 → 你的算法回 result/action → Checker 打分 → report.json → 回调 Hub
```

**核心原则：算法是黑盒。** 你不感知场景、数据集、GT、checker；一切输入输出走协议
（obs/result/action/ctl 四个通道）。评测内容（数据、判过标准）由 plugin + 场景文件定义，与算法仓库解耦。

## 2. 先选路径

| | 路径 A：复用已有插件 | 路径 B：新算法类型自建插件 |
|---|---|---|
| 适用 | 你的算法属于已有评测类型（`pipe.slam` 管道SLAM / `nav2d` 2D导航 / `ctrl.invp` 倒立摆 / `manip.force` 接触力控） | 新算法类型（如新感知类） |
| 你要定义 | manifest + SUT（+ CI） | data schema + checker + dataset + 场景文件 + manifest + SUT（+ CI） |
| 工作量 | 半天级 | 需与评测负责人对齐 schema 与判过标准 |

**路径 A 直接跳到 §3.5（manifest）**；路径 B 从 §3 开始按顺序读。

## 3. 定义链逐环详解（路径 B 全量；路径 A 只读 §3.5–§3.7）

### 3.0 名词卡

| 名词 | 是什么 | 在哪 |
|---|---|---|
| **body** | 本体资产：机器人型号 + 传感器布置（类型→实例→topic）+ 外参 | `body/*.yaml`（已有：`pbox_v1` / `invp_sim` / `nav2d_sim` / `manip_sim`，通常不需新建） |
| **plugin** | 某算法类型的评测包：数据 schema + checker + 数据源 | `plugins/<命名空间>/`（如 `plugins/ctrl.invp/`），每包附 `contract.md` 数据契约 |
| **场景文件** | 一次评测跑什么数据、用什么判定：body + dataset + checker + 传感器/超参 | 你的仓 `scenarios/*.yaml` |
| **manifest** | 算法侧静态声明：launch + consumes + **场景清单** + runtime | **你的算法仓库根目录 `scenario.yaml`** |
| **SUT** | 被测算法进程（你的代码，黑盒） | 你的算法仓库 |
| **World** | 数据源抽象：数据集回放 / 仿真 / 真实设备三形态透明切换 | 框架 `autotest.world.*` |

### 3.1 body（本体资产）—— 了解即可

- 所有评测必须声明 body（场景文件的 `body: <名>`），数据集与本体对齐校验由框架 fail fast。
- 你唯一需要关心的：body 定义 `sensor_config`（{传感器类型: {实例名: topic}}），INIT 时下发给你；
  你 manifest 里 `required_sensors` 声明的实例名必须被它覆盖。
- 新机器人型号才需要新建 body.yaml（找评测负责人）。

### 3.2 plugin 之一：data schema（数据格式）

**文件 `plugins/<ns>/data.py`** —— 定义三种 payload 与跨进程编解码：

| payload | 方向 | 说明 |
|---|---|---|
| observation | World→你 | 每帧观测（如 `SlamData`：多实例传感器容器 + odom） |
| result/action | 你→World | 开环回 result（如位姿），闭环回 action（如速度/力矩指令） |
| ground_truth | World→checker | GT（进程内传递、**不编码**，如轨迹/目标点/障碍） |

- 每个 schema 有命名空间键（如 `pipe.slam.SlamObs`），用 `register_data("observation"|"result", 键, 解码, 编码)`
  注册；编码统一 msgpack，二进制字段（点云）走 `{shape, dtype, data:bytes}`。
- **这是路径 B 最关键的对外契约**：observation 决定你每帧收到什么，result/action 决定你要回什么。
  定稿前与评测负责人对齐。各插件的字段级数据格式见其 `contract.md`（如
  [plugins/pipe.slam/contract.md](../plugins/pipe.slam/contract.md)）。

### 3.3 plugin 之二：checker（判过标准）

**文件 `plugins/<ns>/checker.py`** —— 实现 `IChecker.evaluate(records, ground_truth, config) -> Score`：

- `consumes` 声明依赖的观测 schema（装配期校验 produces⊇consumes，fail fast）。
- 输入：records（开环=你的 result 列表；闭环=observation 轨迹）+ GT 信封 + 阈值配置（`checker_config`）。
- 输出：`Score(metrics={...}, passed=bool)`。metrics 进报告，passed 决定 CI 红绿。
- 参考：[pipe.slam APE/RPE](../plugins/pipe.slam/checker.py)（开环）、[ctrl.invp 回稳判定](../plugins/ctrl.invp/checker.py)（闭环·最简）。

### 3.4 plugin 之三：dataset / world（数据来源）

三形态对算法**完全透明**（同一套协议，只是 World 不同）：

| 形态 | 注册键示例 | 用途 |
|---|---|---|
| 合成/回放 | `pipe.slam.synthetic` / `pipe.slam.rosbag` | 离线数据集逐帧喂（开环主形态） |
| 仿真闭环 | `ctrl.invp.sim` / `nav2d.sim` / `manip.force.sim` | World 收你的 action 推进状态（闭环主形态） |
| 实时流/真机 | `pipe.slam.rostopic` / `pipe.slam.device` | 接 ROS topic / 真实设备 |

- 离线数据集类实现：`testcases` / `frames(testcase_id)` 逐帧产 observation 信封 /
  `ground_truth(testcase_id)` 产 GT 信封，并声明 `produces`。
- 闭环仿真类实现 `IWorld`：`reset/step(action)/get_ground_truth`，参考 [ctrl.invp sim](../plugins/ctrl.invp/sim.py)。
- 注册：`register_dataset("<ns>.<名>", ...)`（见各插件 `__init__.py`）。

### 3.5 manifest（算法仓库根目录 `scenario.yaml`）★ 你必写

最小形态（单场景）：

```yaml
launch: "python3 main.py"            # 启动命令（相对本文件目录执行）
consumes: ["pipe.slam.SlamObs"]      # 你消费的 observation schema（须与插件一致）
scenario: scenarios/smoke.yaml       # 单场景引用（旧式，兼容）
required_sensors:                    # 所需传感器实例（握手时按 body 校验）
  lidar: [front]
hyperparams: {}                      # 超参默认值（与场景合并后 INIT 下发）
```

推荐形态（**场景清单**，R2 权威格式；Hub 手动触发勾选的就是它）：

```yaml
launch: "python3 main.py"
consumes: ["pipe.slam.SlamObs"]
required_sensors: { lidar: [front] }
hyperparams: {}

runtime: { type: venv }              # 可选：依赖隔离（host 缺省 / venv / docker[F2 期]）

scenarios:
  - id: smoke                        # ^[a-z0-9_]+$；Hub 勾选与 submit.scenario 引用它
    description: 快速冒烟（PR 反馈）
    scenario: scenarios/smoke.yaml
  - id: full
    description: 完整回归
    scenario: scenarios/full.yaml
    hyperparams: { kp: 4.0 }         # 深合并覆盖（清单项 > 场景文件 > manifest 默认）
    checker_config: { ate_threshold: 0.3 }
```

**字段全集、清单约束、runtime 语义、错误码 → [scenario.yaml Schema](scenario-schema.md)（权威）。**

### 3.6 场景文件（scenarios/*.yaml）

```yaml
body: pbox_v1                        # 必填：本体资产
dataset:
  type: pipe.slam.synthetic          # 数据源（命名空间键）
  config: { n_testcases: 2, n_steps: 50 }
checker: pipe.slam.ape               # 判过（空 = 只验证数据流）
checker_config: { ate_threshold: 0.2 }
sensor_config:                       # INIT 下发给算法（实例名须与观测一致）
  lidar: { front: /rslidar_points_front }
hyperparams: {}                      # 场景级算法超参
```

装配期三重校验（fail fast，错误信息明确）：body 对齐 / produces⊇consumes / 注册键存在。

### 3.7 SUT（算法进程）★ 你必写

用 SDK（`autotest.sdk.SutBase`）只需覆写 **4 个钩子**：

```python
class MyAlgo(SutBase):
    module = "pipe.slam"              # 命名空间

    def on_init(self, config): ...    # 收 sensor_config+hyperparams → 回能力宣告（可选覆写）
    def on_reset(self, meta): ...     # 每个 testcase 前：清状态、保模型
    def on_step(self, observation):   # 每帧：解码→推理→回 Result(开环)/Action(闭环)
        data = decode_observation(observation["data"])
        return msg.Result(self.module, encode_result("pipe.slam.StampedPose", out))
    def on_terminate(self, reason):   # 收尾：可回自统计 dict（进报告 comm_health）
        return {"comm": self.comm_stats()}
```

- 会话身份（`AUTOTEST_SESSION`/`AUTOTEST_TOPICS`）由 Service 注入，SDK 自处理；**话题名不硬编码**。
- **时钟以 STEP 的 `timestamp` 为准**，禁读墙上时钟（Service 可加速回放）。
- reset 语义：同实例跨 testcase 复用，**清运行状态、保留模型/参数**。
- 参考实现：[examples/slam_algo.py](../examples/slam_algo.py)（开环）、[examples/invp_sut.py](../examples/invp_sut.py)（闭环·最简 PD 样例）、[examples/nav_sut.py](../examples/nav_sut.py)（闭环·导航）、[examples/manip_sut.py](../examples/manip_sut.py)（闭环·力控）；ROS2 算法经 [ros2_pipe_bridge.py](../examples/ros2_pipe_bridge.py) 桥接。

### 3.8 协议与生命周期（SDK 已封装，调试/原生接入时读）

所有消息是可 msgpack 的 dict：`{"type": <类型>, "session_id": <会话号>, "payload": {...}, "seq": <帧序号>}`。

| type | 方向 | payload | 你回什么 |
|---|---|---|---|
| `init` | Service→你 | `{sensor_config, hyperparams}` | `ready` |
| `ready` | 你→Service | `{module, version, required_sensors}` | — |
| `reset` | Service→你 | `{testcase_id}` | `reset_ack{ok}` |
| `step` | Service→你 | `{done, observation}` | `result`（开环）/ `action`（闭环） |
| `terminate` | Service→你 | `{reason}` | `final` |

时序：`INIT→READY` 宣告能力 → 每个 testcase 先 `RESET`（清状态、保模型）→ 逐帧 `STEP`，
每帧异步回 result/action → 全部跑完 `TERMINATE→FINAL`。

- 指令走 `ctl` **service**（一问一答）；帧数据走 `obs` **topic**（不回确认）。
- 一帧可回多个 result，也可攒多帧回一个；结果异步发，不受 step 频率约束。
- `seq` 是 Service 推流帧序号（0 起递增），丢帧排查用，你可忽略。
- 多场景评测 = 每场景独立拉起进程 + 独立会话（场景间不共享你的进程状态）。

### 3.9 CI（Hub 直连，主通路）

算法仓只要根目录有 manifest（`scenario.yaml`），Hub 即按坐标（repo+ref）触发评测——ATP 在评测机
checkout（mirror 缓存 + worktree 隔离）并执行，终态主动回调 Hub。**算法仓无需拷贝任何 workflow、
无需配置回调 Secret**；前置仅为 ATP 评测机预置该仓的只读 deploy key。

日常使用（场景勾选 / 基线 / 回归语义 / 排障）见 [CI集成.md](CI集成.md)。

## 4. 运行与调试归因

### 4.1 本地开发机自测（不走 HTTP 服务）

```bash
python3 -m autotest.client run <算法仓库>/scenario.yaml [--scenario 覆盖场景文件] [--clock-rate 1.0] [--json]
```

> 环境前提：本机 tzcomm daemon 与 autotest server 已启动；未 pip 安装时用
> `PYTHONPATH=<atp仓库绝对路径>/src`（**必须绝对路径**——SUT 子进程工作目录会切到 manifest 所在目录）。

生产同款通路（推荐联调）：`python3 -m autotest.client atp submit --repo <仓> [--scenario <id>]`
（env：`ATP_BASE_URL` / `ATP_SERVICE_TOKEN`），或浏览器 `<ATP_BASE_URL>/console` 表单。

### 4.2 暂停/单步（调试算法时）

评测跑到一半想看算法现场（attach 调试器、打印中间量）？另开一个终端对运行中的 job 发调试命令：

```bash
python3 -m autotest.client pause <job_id>        # 世界冻结：停喂帧，SUT 安全等待
python3 -m autotest.client step <job_id> -n 10   # 暂停中单步放行 10 帧（默认 1）
python3 -m autotest.client resume <job_id>       # 恢复全速
```

- 暂停语义：World 停喂帧、时钟冻结，SUT 阻塞等下一帧——观察/断点的安全态，不会因超时被框架判死。
- `step` 仅在暂停中有效；`resume` 后残余配额作废，不会多走"幽灵帧"。开环闭环同样适用。

### 4.3 链路预检（怀疑 tzcomm 时先跑）

```bash
python3 -m autotest.commcheck          # daemon 可达 / SUBPUB 回环 / Service 回环，退出码 0/1
```

### 4.4 归因速查（框架 vs tzcomm vs 算法 vs 配置）

| 症状 | 看哪里 | 归因 |
|---|---|---|
| 提交即 400，`code: scenario_unknown` | 报文含可用场景清单 | submit.scenario 拼写/清单未同步（**配置**，改 id 重提） |
| 提交即 400，`code: manifest_missing / manifest_invalid` | 报文指明缺失/非法项 | 仓内 scenario.yaml（**配置**，对照 [Schema](scenario-schema.md)） |
| results 含 `<runtime>` 失败条目 | session.log `[runtime]` 段 | venv/pip 依赖安装失败，或 docker（F2 期未实现）（**环境**） |
| results 含 `场景id:<scenario>` 失败条目 | session.log 对应场景段 | 该场景装配/执行异常（其余场景不受影响，逐个排） |
| `comm_health.warnings` 非空 | 双侧丢包率超 1% | **tzcomm 链路**（丢包），把报告发给 tzcomm 负责人 |
| SUT 进程未拉起 / 无 ready | session.log launch 报错 | manifest `launch` 或环境（`PYTHONPATH`/venv） |
| 装配期 fail fast | 报错直指缺失项 | 场景/manifest 声明不一致（schema 键、传感器实例名、body） |
| 收不到帧 / 卡 step | `TZCOMM_LOG_LEVEL=DEBUG` 起 SUT | 发现层/话题名 |
| metrics 异常但链路正常 | checker 的 metrics 与 GT | **算法本身** |
