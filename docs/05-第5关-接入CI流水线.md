# 第 5 关：接入 CI 流水线

> **学习目标**：理解三个平台各管哪一段，让评测在你 push 代码时自动发生，并知道结果会落到哪几个地方。
> **前置**：完成第 1–3 关（第 4 关可选）。你的算法已经能被 `client run` 跑通。
> **用时**：读 30 分钟 + 配置 30 分钟。**角色**：算法工程师和测试工程师都读。

---

## 5.1 为什么需要第三方来触发

到第 4 关为止，你都是手动敲 `client run`。手动跑有三个问题，而且都是**人的问题，不是技术问题**：

1. **会忘**。赶进度的时候，"这个改动很小，不用跑了吧" 是最常见的回归入口。
2. **不统一**。你跑的是 smoke，同事跑的是 full，两份结果不可比。
3. **结果不留痕**。跑完在你终端里，评审的人看不到，三个月后没人说得清那个版本当时测过什么。

CI 解决的就是这三件事：**必然发生、口径统一、结果挂在代码和人身上**。

## 5.2 三个平台，各管一段

```
   ┌─────────┐   webhook    ┌──────────┐   HTTP submit   ┌──────────┐
   │ GitHub  │─────────────▶│   Hub    │────────────────▶│   ATP    │
   │         │              │(cicd-hub)│                 │(评测机)   │
   │         │◀─────────────│          │◀────────────────│          │
   └─────────┘  check-runs  └──────────┘   评测完成回调    └──────────┘
                              │      ▲
                    ci-results│      │  tasks / repos
                              ▼      │
                          ┌──────────────┐
                          │     PMS      │──▶ 飞书通知
                          │  (任务卡)     │
                          └──────────────┘
```

| 平台 | 事实源 | 一句话 |
|---|---|---|
| **ATP** | **评测执行事实** | 在评测机上跑测试、出报告、留现场 |
| **Hub** | **流水线事实** | 收 GitHub 事件、决定该跑什么、调度 ATP、把红绿写回 PR |
| **PMS** | **人与任务事实** | 把结果贴到任务卡上、发飞书通知、管交付物 |

三者**不共享数据库**，靠一个贯穿全链路的 `correlation_id`（形如 `chk_01J...`）对账。

### 一条必须理解的设计原则

> **Hub 不传递评测逻辑，只传递坐标。**

Hub 发给 ATP 的请求里只有：哪个仓（`repo`）、哪个分支（`ref`）、跑哪几个场景 id（`scenario`）、要不要滚基线（`save_baseline`）。

**"该怎么测"这件事，全部来自 ATP 在评测机上 checkout 出来的你的仓库内容**——你的 `scenario.yaml` 和 `scenarios/*.yaml`。

这跟 GitHub Actions 是同一个道理：

| GitHub Actions | 这套框架 |
|---|---|
| `.github/workflows/*.yml` 在你仓里 | `scenario.yaml` + `scenarios/*.yaml` 在你仓里 |
| runner 只是执行器 | ATP 只是执行器 |
| 改测试 = 改仓里的 yaml 再 push | 改测试 = 改仓里的 yaml 再 push |

**推论（也是新人最常问的问题）**：**不存在"在 ATP 平台上上传测试用例"的界面。** 测试定义的权威在你的仓里，好处是测试和代码同仓评审、同版本演进——checkout 到哪个 commit，就用那个 commit 当时的测试定义。

## 5.3 一次自动评测的完整链路

```
① 你 push 代码到算法仓
         │
② GitHub 发 push/PR webhook 给 Hub
         │
③ Hub 生成 correlation_id，落一条 pending 记录（repo, sha, 超时时刻），
   按 repo↔ATP 路由挑一台评测机
         │
④ Hub ─POST /atp/evaluations─▶ ATP
   报文：{correlation_id, repo, ref, sha, check_type: "autotest",
          scenario: null|"id"|["a","b"], save_baseline, pms_task_id}
   ATP 回 202 {ok, job_id, sha}
   （同一个 cid 重复提交是幂等的：返回 duplicate:true，不重复执行）
         │
⑤ ATP 在本机 workspace 按 repo+ref checkout 你的代码
   （评测机预置了你仓的只读 deploy key）
         │
⑥ ATP 读仓根 scenario.yaml → 选场景 → 逐场景评测
   （单台 ATP 串行执行，评测机资源独占；Hub 侧排队）
         │
⑦ 评测完成（含失败），ATP 主动回调 Hub /api/ci/callback
   报文：{correlation_id, sha(实际checkout的), check_type, conclusion,
          report: {summary}, finished_at}
   summary 里带逐场景 passed/metrics + vs_baseline 计数
         │
⑧ Hub 归位：写 GitHub check-run（PR 上的 ✅/❌ + 摘要 + 详情链接）
         │
⑨ Hub 推 PMS /pms/ci-results → 结果出现在任务卡「CI 结果」区块 → 飞书通知
```

**兜底**：如果第 ⑦ 步的回调没到（网络抖动等），Hub 会轮询 `GET /atp/evaluations/{job_id}` 判终态；再不行就标 timeout 告警。**结果不会丢**。

**触发即失败的快路径**：如果第 ④ 步 ATP 就发现有问题（token 错、ref 不可达、manifest 缺失或非法），直接返回 4xx，Hub 立刻判红，**不用等超时**。错误码见 §5.7。

## 5.4 你要做什么（很少）

**日常你只维护一个东西：仓内的 `scenario.yaml`。** 算法仓**零 workflow、零 Secret**——不用拷贝任何 CI 配置文件，不用配回调密钥。

一次性前置（缺一不可，但都是别人做的）：

| # | 前置 | 谁做 |
|---|---|---|
| 1 | ATP 评测机预置你仓的**只读 deploy key**（没有它 ATP checkout 不到代码） | 评测负责人 |
| 2 | 你的仓在 Hub 的 ATP 路由里注册（哪个仓派给哪台评测机） | Hub 管理员（console「设置 → ATP 池」界面配置） |
| 3 | PMS 里把任务绑定到你的仓（可选，但绑了结果才会出现在任务卡上） | 你 / 项目负责人 |

第 3 步值得展开一下，因为它决定了"结果给谁看"：

- 入口有两个，等价：任务抽屉编辑表单的「仓库」复选框，或项目后台 Hub 面板 repo 区块的「绑定任务」下拉。
- 绑定之后，该 repo 的 push/PR 评测结果**自动**出现在所有绑定了它的任务卡上，不用每次指定。
- 归属关系分三档强度，任务卡上用徽章区分：**交付物绑定 = 强**、**手动触发时显式指定 = 强**、**repo 绑定推导 = 中**。

## 5.5 手动触发：`mannultest` 分支族

想在合入前先测一把？用 Hub 的手动触发。前提是**ATP 得有代码可以 checkout**，所以要先把代码推到一个约定前缀的临时分支：

```bash
git checkout -b mannultest/<你的名字>/<时间戳>       # 如 mannultest/zhangsan/20260827_1530
git push -u origin mannultest/<你的名字>/<时间戳>
```

然后在 Hub 手动触发页面填表：

| 字段 | 说明 |
|---|---|
| repo | 你的算法仓（`owner/repo`） |
| ref | 下拉会**自动列出**该仓的 `mannultest/*` 候选，不用手输 |
| scenario | **勾选**——列表来自你仓 `scenario.yaml` 的 `scenarios:` 清单（`id` + `description`）。不勾 = 全跑 |
| pms_task_id | **必填**。下拉列出已绑定任务的 `record_id · 标题（状态）` |

几个要点：

- **为什么必须是这个前缀**：Hub 会校验前缀，其他 ref 一律拒绝。这条约定的唯一职责就是"让 ATP 有代码可 checkout"，同时防止绕过 cid 直接触发。
- **评测终态后 Hub 自动清理临时分支**，不用手删。
- **手动测试的语义是"仅预验证"**——它不作为交付附件，任务卡上会明确标注「手动测试」徽章，和自动通路的结果区分开。
- **改了场景清单 push 就生效**：Hub 是经 GitHub Contents API 现读你仓里的文件，不需要通知 ATP。

**不想开浏览器？** 命令行直接打 ATP（和 Hub 用的是同一个接口）：

```bash
python3 -m autotest.client atp login          # 一次性：录入服务地址 + 令牌，落盘 ~/.config/autotest/client.env
python3 -m autotest.client atp whoami         # 自查：当前配置来源 + 掩码令牌 + 探活
python3 -m autotest.client atp submit --repo <owner/repo> --ref <分支> --scenario smoke
# 默认阻塞等终态并输出 summary；--no-wait 只提交不等；同 --cid 幂等可安全重放
# 评测失败退出码为 1，可以直接接脚本做 gate
```

`--repo` 也接受**评测机本地路径**（联调时很方便），但注意：**走 Hub 链路时必须是 `owner/repo` 的 GitHub 坐标**，本地路径只在直连 ATP 时可用。

CI/脚本注入场景仍可用环境变量 `ATP_BASE_URL` / `ATP_SERVICE_TOKEN`，它们**优先于**配置文件。

## 5.6 结果落在哪：四个入口

| 入口 | 看得到什么 | 什么时候用 |
|---|---|---|
| **GitHub check-run**（PR 页面） | ✅/❌ + summary（逐场景 passed/metrics/vs_baseline）+ 详情链接 | 评审时一眼看红绿 |
| **PMS 任务卡「CI 结果」区块** | 按 commit 分组的结果、来源徽章、手动测试标记、完成时间 | 追踪"这个任务测得怎么样了" |
| **ATP console**（`<ATP地址>/console`） | 评测列表、展开详情、手动触发、健康与队列 | 排查具体某次评测 |
| **评测机 `artifacts/<job_id>/`** | `report.json` 全量明细 + `session.log` 执行流水 | **深挖问题的最终现场** |

排查顺序建议：check-run 的 summary → console 详情 → `session.log`。归因速查表见[速查手册](06-速查手册.md)。

## 5.7 触发即失败：三个错误码

这三种情况 ATP 在提交阶段就返回 4xx，Hub 直接判红。它们**都是配置问题，不是算法问题**：

| code | 含义 | 怎么修 |
|---|---|---|
| `manifest_missing` | 仓里找不到 `scenario.yaml` | 确认它在**仓根**并且已经 push 了 |
| `manifest_invalid` | manifest 解析/校验失败 | 报文会指明具体哪一项：缺 `launch`、清单项缺 `id`/`scenario`、`id` 非法或重复、`runtime.type` 未知 |
| `scenario_unknown` | 勾选的场景 id 不在清单里 | **报文会带上可用清单**（`未知 scenario: xxx（可用: a, b）`），改选或同步清单 |

执行期的失败（算法没起来、场景装配失败、判据判红）不走这条路，看 summary 和 `session.log`。

## 5.8 基线在 CI 里的语义

第 3 关讲了基线的概念，这里是它在 CI 里的具体运作：

| 触发场景 | `save_baseline` | 语义 |
|---|---|---|
| PR / 特性分支 | `false` | **只对比，不滚动**。基线代表主干水平，不该被特性分支污染 |
| 主干合入 / 发版 | `true` | **先对比，后滚动**。新的主干水平被锁定 |
| 手动触发 | 表单可勾 / `atp submit --save-baseline` | 按需 |

回调 summary 里带 `vs_baseline` 计数：

```json
"vs_baseline": { "new": 1, "improved": 2, "regressed": 0, "worse": 1, "same": 5 }
```

**PR 红了怎么办——决策树：**

```
check-run 红了
    │
    ├─ code 是 manifest_* / scenario_unknown ？
    │     └─ 配置问题，照 §5.7 修，跟算法无关
    │
    ├─ summary 里有 <runtime> 失败条目？
    │     └─ venv/依赖装不上，看 session.log 的 [runtime] 段
    │
    ├─ comm_health.warnings 非空（丢包 > 1%）？
    │     └─ 底层通信问题，不是你的算法，把报告发给通信负责人
    │
    ├─ 某个场景整体失败（`场景id:<scenario>` 条目）？
    │     └─ 该场景装配/执行异常，其余场景不受影响，看 session.log 对应段
    │
    └─ 是 testcase 的 passed=false / regressed？
          └─ 真的是算法问题。看 metrics 差在哪 → 回第 2 关本地复现调试
             （⚠ 不许通过放宽阈值或滚动基线来"修复"）
```

最后那条注解是[导读](00-导读与学习路径.md) §4 黄金纪律在 CI 里的形态。**基线滚动的权限要和代码合入的权限一样严肃。**
