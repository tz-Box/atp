# 快速上手：30 分钟跑通第一次评测

> 读者：第一次使用 ATP 的工程师。
> 目标：用一个**照抄即可跑**的最小例子，走通"算法仓 → 提交评测 → 看结果"全流程。
> 深入阅读（门户左侧按序号由浅入深）：[算法接入手册](02-算法接入手册.md)（协议/SDK/插件开发）、
> [scenario.yaml Schema](03-scenario-schema.md)（字段权威表）、[CI 集成](04-CI集成.md)（接 Hub 自动触发）。

## 0. 先对齐三个认知（3 分钟，最重要的一节）

### 0.1 ATP 不会替你发明测试

你的直觉是对的：**只写一个 scenario.yaml，做不了"任何"测试**——它只能对应到提前准备好的测试。

ATP 的定位是**通用执行器**，不是测试生成器。它只做四件事：

```
checkout 你的仓 → 按声明拉起你的算法进程 → 喂【准备好的】数据 → 按【准备好的】判据打分 → 出报告
```

"喂什么数据、怎么判过"必须**提前存在**。类比 GitHub Actions：`workflow.yaml` 本身不产生测试，
它只是声明"跑哪些已存在的测试命令"；ATP 的 `scenario.yaml` 同理，声明"跑哪些已存在的场景"。

那测试从哪来？两条路：

- **复用平台已备好的**：ATP 内置了若干算法类型的数据源与判过器（SLAM 精度、倒立摆回稳、2D 导航、
  力控……），你按名字引用即可——本教程走的就是这条路，零基础 30 分钟跑通。
- **自建新的**：你的算法类型平台还没有？那需要开发"插件"（新数据源 + 新判过器），
  这是一次性的评测基建工作，见 [算法接入手册](02-算法接入手册.md) 路径 B。

### 0.2 三个 YAML 各管一件事

```
① 你的仓根 scenario.yaml      ← 入口声明：怎么启动你的算法 + 跑哪些场景（清单）
        │ 按清单引用
        ▼
② scenarios/*.yaml（场景文件） ← 测试内容：喂什么数据、按什么标准判过
        │ 按名字引用
        ▼
③ ATP 平台内置插件             ← 数据源/判过器的具体实现（平台已备好，你不用写）
```

- ①② 在**你的算法仓库**里，是你的交付物；③ 在 ATP 平台侧，开箱即用。
- 报错信息里的 **manifest** 一词 = ① 仓根 `scenario.yaml`（内部术语，同一个文件，别被吓到）。
- 一次评测 = 按 ① 的清单逐个跑 ②；提交时可以只选其中一个场景跑（§3）。

### 0.3 两个角色，入门时你一人分饰

| 角色 | 职责 | 本教程中对应文件 |
|---|---|---|
| **算法工程师** | 让算法能"收观测帧、回结果"：写算法进程 + 仓根入口声明 | `sut.py` + `scenario.yaml` |
| **测试工程师** | 定义"考什么"：选数据源、定判过阈值、维护场景分级 | `scenarios/smoke.yaml` |

现实中常是同一个人，但**心智上请分开**：改算法不动场景，改判过标准不动算法。
本教程三个文件照抄，相当于把两个角色的活各干了一遍。

## 1. 登录 ATP（2 分钟，一次就好）

ATP 服务由团队部署在评测机上。找评测负责人拿两样东西：**服务地址**（如
`http://atp.turing-zero.com`）和**服务令牌**（一串密钥文本）。

本机装好 `tz_atp` 包后（在 ATP 仓 `pip install --user -e .`），一次登录，永久免配置：

```bash
python3 -m autotest.client atp login
# ATP 服务地址 [http://127.0.0.1:2335]: http://atp.turing-zero.com   ← 粘贴地址，回车
# ATP 服务令牌（输入不回显）:                                          ← 粘贴令牌，回车
# 已保存 → ~/.config/autotest/client.env（chmod 600）
# 探活成功：v0.x.x · 队列 0，可以使用了
```

登录后随时自查（地址/令牌来源、掩码显示、服务探活）：

```bash
python3 -m autotest.client atp whoami
```

> - 令牌只存本机 `~/.config/autotest/client.env`（权限 600，仅自己可读）；`atp logout` 即删除。
> - 环境变量 `ATP_BASE_URL` / `ATP_SERVICE_TOKEN` 仍然受支持且**优先于**配置文件——CI 注入或临时切换时用。
> - 不想装命令行？浏览器打开 `<服务地址>/console`，飞书登录后用网页表单，效果相同。

## 2. 最小算法仓（15 分钟，照抄三个文件）

建一个目录（这就是你的"算法仓"），最终长这样：

```
my_algo/
├── scenario.yaml          # ① 入口声明（算法工程师）
├── sut.py                 #    算法进程：回声示例（算法工程师）
└── scenarios/
    └── smoke.yaml         # ② 场景文件：最小冒烟（测试工程师）
```

### 2.1 `scenario.yaml` —— 入口声明（逐行讲解）

```yaml
launch: "python3 sut.py"             # ATP 用这条命令拉起你的算法（在本文件所在目录执行）
consumes: ["pipe.slam.SlamObs"]      # 声明：我的算法消费"管道SLAM观测"这种数据（③ 里插件定义的名字）
required_sensors: { lidar: [front] } # 声明：我的算法需要一个名叫 front 的激光雷达
hyperparams: {}                      # 算法超参默认值（先空着，INIT 时会下发给算法）
scenarios:                           # 场景清单：这个仓提供哪些测试
  - id: smoke                        #   场景 id（小写字母/数字/下划线），提交评测时按它选
    description: 最小冒烟场景          #   给人看的说明（Hub 勾选列表也显示它）
    scenario: scenarios/smoke.yaml   #   指向 ② 场景文件
```

**它只回答两个问题**：怎么启动你（`launch`）、有哪些测试可跑（`scenarios` 清单）。
它**不包含**测试内容本身——那是 ② 的事（呼应 0.1：声明 ≠ 测试）。

### 2.2 `scenarios/smoke.yaml` —— 场景文件（逐行讲解）

```yaml
body: pbox_v1                    # 用哪款机器人本体（传感器布置；pbox_v1 是平台内置资产）
dataset:
  type: pipe.slam.synthetic      # 数据源：合成 SLAM 数据（平台内置插件，零外部依赖，凭空造数据）
  config: { n_testcases: 2, n_steps: 30 }   # 造 2 条轨迹、每条喂 30 帧
checker: pipe.slam.ape           # 判过器：轨迹精度 APE（平台内置插件）
checker_config: { ate_threshold: 0.5, rpe_threshold: 0.05 }  # 判过阈值（测试工程师的尺子）
sensor_config:
  lidar: { front: /points }      # 传感器的 topic 名（实例名 front 与 ① 的 required_sensors 对齐）
```

**这一份才是"提前准备好的测试"本体**：数据从哪来（`dataset`）、什么叫过（`checker` + 阈值）。
`pipe.slam.synthetic` 和 `pipe.slam.ape` 都是 ③ 平台内置插件的注册名，照抄引用即可。
字段全集见 [scenario.yaml Schema](03-scenario-schema.md)。

### 2.3 `sut.py` —— 算法进程（逐段拆解）

完整代码先贴全（这是一个"回声算法"：收到里程计原样回传，是协议的最小完整实现）：

```python
from autotest.protocol import messages as msg
from autotest.protocol.schema import Pose, StampedPose, decode_observation, encode_result
from autotest.registry import load_plugin
from autotest.sdk import SutBase

load_plugin("pipe.slam")  # 注册 pipe.slam schema 编解码器


class EchoSlam(SutBase):
    module = "pipe.slam"

    def on_reset(self, testcase_meta):    # 每个 testcase 前：清状态、保模型
        pass

    def on_step(self, observation):       # 每帧观测 → 回结果
        data = decode_observation(observation["data"])  # SlamData
        pose = data.odom if data.odom is not None else Pose(0, 0, 0, 0, 0, 0, 1)
        return msg.Result(
            "pipe.slam",
            encode_result("pipe.slam.StampedPose",
                          StampedPose(timestamp=observation["timestamp"], pose=pose)),
        )


if __name__ == "__main__":
    EchoSlam("echo-slam").spin()
```

**逐段拆解**（哪些是通用的、哪些是 SLAM 专属的，看清楚就不懵了）：

**段 1：import 与 `load_plugin`**

- `SutBase`（通用）：SDK 基类。ATP 与你的进程之间的消息收发、会话建立、帧循环**全部封装在它里面**，
  你只需覆写几个钩子函数，不用碰任何网络/协议细节。
- `decode_observation` / `encode_result`（通用）：观测帧是跨进程传来的字节流，这对函数负责
  字节 ↔ Python 对象的转换。
- `load_plugin("pipe.slam")`（SLAM 专属）：**为什么可以 load？** ATP 把每种算法类型的数据格式做成
  "插件"内置在包里，`load_plugin` 就是按名字把 `pipe.slam` 这个插件的编解码器注册进来——注册之后，
  上面的 decode/encode 才认识 `SlamObs`、`StampedPose` 这些类型。不 load 就会在解码时报"未知 schema"。
- **想写自己的插件？**（新算法类型，自定义数据格式 + 判过器）那是路径 B，
  见 [算法接入手册](02-算法接入手册.md) §3.2–§3.4——入门阶段不需要。

**段 2：类声明与 `module`**

- `module = "pipe.slam"`（SLAM 专属）：告诉 ATP"我是管道 SLAM 类算法"，与 ① 的 `consumes` 对应。
- `EchoSlam("echo-slam")` 的名字只是实例标识，随意。

**段 3：`on_reset`（通用钩子）**

- 每条 testcase 开跑前 ATP 调一次。语义：**清运行状态、保留模型/参数**（同进程会跨 testcase 复用）。
- 回声算法无状态，所以 `pass`。你的算法如果有积分器、滤波器、地图，在这里重置。

**段 4：`on_step`（核心钩子，逐行看）**

- 每收到一帧观测，ATP 调一次；你 return 什么，什么就是"算法输出"，交给判过器打分。
- `decode_observation(observation["data"])`（通用调用，SLAM 专属返回类型）：得到 `SlamData` 对象——
  里面有传感器数据和 `odom`（里程计）。字段细节见插件的数据契约（手册 §3.2 有索引）。
- `pose = data.odom if ... else Pose(...)`（回声逻辑）：有里程计就原样回，没有就回一个单位位姿占位。
  **换成你的算法，这两行就是你的推理代码**（输入观测 → 算出位姿）。
- `msg.Result(...)`（通用）：把结果包好回传；`encode_result("pipe.slam.StampedPose", ...)`（SLAM 专属
  类型名）：按声明的类型编码。**时钟必须用 `observation["timestamp"]`**，禁读墙上时钟（ATP 可加速回放）。

**段 5：`spin()`（通用）**

- 进入帧循环：等 INIT → 宣告就绪 → 逐 testcase 收 RESET/逐帧收 STEP → 跑完收 TERMINATE。
  整个生命周期由 SDK 驱动，你不用管。

**换成你的算法，要改的就 4 处**：

| 改哪里 | 改成什么 |
|---|---|
| `load_plugin("pipe.slam")` | 你的算法类型对应的插件名（没有 → 路径 B 自建） |
| `module` | 同上，保持命名空间一致 |
| `on_step` 里的两行回声逻辑 | 你的推理代码 |
| `encode_result` 的类型名与字段 | 你的输出类型（插件契约里查） |

## 3. 提交评测（2 分钟）

**方式一：console 网页（推荐首次）**——浏览器打开 `<服务地址>/console`，飞书登录后
在"手动触发评测"表单填：

- repo：`/path/to/my_algo`（评测机本地路径，**仅限直连 ATP**；走 Hub 链路必须 `owner/repo` GitHub 坐标，见 [CI 集成](04-CI集成.md) §1）
- scenario：`smoke`（选单个场景；留空 = 清单全跑——本例只有一个，效果相同）
- 提交后，下方评测列表实时刷新状态，点行展开详情。

**方式二：命令行**（已 `atp login`，零配置）：

```bash
python3 -m autotest.client atp submit --repo /path/to/my_algo --scenario smoke
# stderr 打出 job_id，阻塞等待终态后输出结果 JSON；评测失败退出码为 1（可直接接脚本 gate）
```

> 重复提交同一 `correlation_id` 是幂等的（返回 `duplicate: true`），安全重放不会重复执行。

## 4. 看结果（3 分钟）

console 展开详情，或命令行 `atp status <job_id>` / `atp wait <job_id>`。关键字段：

```json
{
  "status": "success",                    // success / failure / running
  "summary": "2/2 passed; tc-1: passed (ate_rmse=...); ...",
  "vs_baseline": {"new": 2}               // 与滚动基线对比（首次评测全记 new，正常）
}
```

- `passed` 由 checker 按 `checker_config` 的阈值判定；metrics（如 `ate_rmse`）进报告。
- 回声算法对合成数据源应 **2/2 全过**——如果挂了，九成是环境/路径问题，按下面顺序排：
  1. 提交即 4xx → 看报文里的 `code` 和可用清单（拼写、清单、文件缺失，属配置问题）；
  2. 评测 failure → console 详情里的 summary 与评测机 `artifacts/<job_id>/session.log`（执行留痕）；
  3. 完整归因速查表（框架 / 通信链路 / 算法 / 配置）见 [算法接入手册](02-算法接入手册.md) §4.4。

## 5. 常见疑问（FAQ）

**Q：为什么没有一个"ATP 端测试目录"让我上传测试？**
A：设计如此——测试定义的权威在**你的仓内**（scenario.yaml + scenarios/），ATP 只是执行器。
好处：测试与代码同仓评审、同版本演进；Hub 勾选场景时读的也是你仓里的清单。

**Q：我想测的内容，平台没有现成的数据源/判过器怎么办？**
A：那是"插件开发"（路径 B）：定义数据格式 + 判过器 + 数据源，一次性基建，
需与评测负责人对齐数据契约。全流程见 [算法接入手册](02-算法接入手册.md) §2、§3。

**Q：一个仓想配多个场景（快速冒烟 + 完整回归）？**
A：① 的 `scenarios` 清单加条目即可，每条可覆盖超参/阈值（深合并）。
写法与约束见 [scenario.yaml Schema](03-scenario-schema.md) §3；CI 里按 id 勾选见 [CI 集成](04-CI集成.md)。

**Q：不想走服务，在开发机上本地自测？**
A：`python3 -m autotest.client run my_algo/scenario.yaml`（本机通路，适合调试算法），
前提与用法见 [算法接入手册](02-算法接入手册.md) §4.1；还有暂停/单步调试（§4.2）。
