# 第 2 关：接入你的算法（Q1 · 考谁）

> **学习目标**：让你自己的算法进程能被 ATP 拉起来、按协议对话、拿到分数。
> **前置**：完成[第 1 关](01-第1关-跑通第一次评测.md)。
> **本关不需要理解**：判据怎么实现、仿真世界怎么写——那是第 4 关。你现在只管"把自己接上去"。
> **用时**：读 40 分钟 + 动手半天。**角色**：算法工程师主场。

---

## 2.1 一条心智：你的算法是黑盒

接入 ATP 时最容易走弯路的，是想把测试逻辑写进算法里。请先接受这条约束：

**你的算法不 import 框架的任何测试组件，不知道自己在被谁测、用什么数据测、及格线是多少。它只做一件事：收观测，回结果。**

| 你**不该**知道的 | 为什么 |
|---|---|
| 当前是哪个场景、哪个 testcase | 知道了就可能针对特定 testcase 调参 = 作弊 |
| 数据是仿真的还是真机的 | 一旦分支处理，"仿真过了真机也过"的推论就不成立了 |
| 真值（Ground Truth）是什么 | 拿到真值就不叫估计算法了 |
| 判据和阈值 | 算法不该为了过线而优化，该为了任务而优化 |

换来的好处是**三源透明**：同一份算法代码，接仿真、接数据集回放、接真机数据流，**一行都不用改**。这不是理想化的说法——框架的 World 抽象就是为此存在的，第 4 关会看到三种 World 如何实现同一个接口。

你实际需要交付的只有两样东西：

```
你的算法仓/
├── scenario.yaml       ← manifest：怎么启动我、我吃什么数据、我提供哪几套题
└── <你的算法进程>       ← 实现协议，4 个钩子
```

## 2.2 会话生命周期：本关唯一需要背下来的东西

一次评测 = 一次**会话**。会话由 5 类消息构成，全部由框架 SDK 处理，你只在钩子里写业务逻辑。

```
ATP 服务                                         你的算法进程
   │                                                  │
   │   （按 manifest 的 launch 命令把你拉起来，        │
   │    注入环境变量 AUTOTEST_SESSION / AUTOTEST_TOPICS）
   │                                                  │
   │── INIT ─────────────────────────────────────────▶│  on_init(config)
   │   {sensor_config, hyperparams, body_profile}     │  ← 读超参，建模型
   │◀─ READY ─────────────────────────────────────────│
   │   {module, version, required_sensors}            │
   │                                                  │
   │ ┌─ 每个 testcase 循环 ───────────────────────────────────────┐
   │ │                                                │           │
   │ │─ RESET {testcase_id} ─────────────────────────▶│ on_reset()│
   │ │◀ RESET_ACK {ok} ───────────────────────────────│           │
   │ │                                                │           │
   │ │─ STEP {observation, done} ────────────────────▶│ on_step() │
   │ │◀ RESULT（开环）或 ACTION（闭环）───────────────│           │
   │ │                    ……逐帧重复……                │           │
   │ │─ STEP {done: true} ───────────────────────────▶│  收尾帧    │
   │ └────────────────────────────────────────────────────────────┘
   │                                                  │
   │── TERMINATE {reason} ───────────────────────────▶│ on_terminate()
   │◀─ FINAL {自统计} ────────────────────────────────│
```

| 消息 | 时机 | 你在钩子里该做什么 |
|---|---|---|
| `INIT` → `READY` | 进程启动后一次 | 读 `hyperparams` 建立模型/控制器；宣告自己需要哪些传感器 |
| `RESET` | **每个 testcase 前一次** | **清运行状态，保留模型/参数/权重** |
| `STEP` | 每帧 | 解码观测 → 推理 → 回 `Result`（开环）或 `Action`（闭环） |
| `TERMINATE` → `FINAL` | 全部跑完一次 | 收尾；可回自统计字典（进报告） |

**三条硬约定，违反了会出各种诡异问题：**

1. **RESET 语义**：清运行状态（积分器、滤波器、地图、轨迹缓冲），**保留**模型权重和超参。同一个进程要跨 testcase 复用，状态残留会让第 2 个 testcase 的结果受第 1 个影响，评测就不可复现了。
   （换超参、换算法版本 = 走完整的新会话，不是 RESET。）
2. **时钟只认 `observation["timestamp"]`，禁止读墙上时钟**（`time.time()`）。框架可以加速或减速回放（`--clock-rate`），也可以暂停单步调试；一旦你读墙上时钟，这些能力全部失效，而且结果不可复现。
3. **话题名不许硬编码**。会话身份由框架经环境变量 `AUTOTEST_SESSION` / `AUTOTEST_TOPICS` 注入，SDK 自动处理。每次评测是不同的会话号。

## 2.3 开环还是闭环：你的算法属于哪一种

这是"测试方式"的第一层选择，决定了你在 `on_step` 里回什么。

| | **开环 · 回放** | **闭环 · 交互** |
|---|---|---|
| 你回什么 | `Result`——**估计量** | `Action`——**控制量** |
| 世界受你影响吗 | **不受**。数据是录好的，你答什么都不改变下一帧 | **受**。你的指令积分进物理，决定下一帧 |
| 典型算法 | SLAM、检测、分割、定位、状态估计 | 控制、导航、运动规划、抓取 |
| 数据从哪来 | 数据集 / rosbag / 真机录制 | 仿真器（必须能回应你） |
| 一个 testcase 是 | **一段录好的数据** | **一个初始状态 + 一套动力学** |
| 判据拿到什么 | 你的 `Result` 序列 + 真值 | 世界的**观测轨迹** + 真值 |
| 复现性 | 天然完美（同数据同帧） | 依赖仿真的确定性（见第 4 关 §4.7） |
| 本仓现有插件 | `pipe.slam` | `ctrl.invp` / `nav2d` / `manip.force` |

**为什么闭环的 testcase 不能是"一段数据"**：控制器施加的力决定了下一帧状态。如果你只回放一段录好的轨迹，那这条轨迹是**别的控制器**产生的，跟被测算法毫无关系。所以闭环必须有一个"会回应"的世界。这正是第 4 关要写 `sim.py` 的原因。

框架**不需要你声明**自己是哪种模式——你回 `Result` 就走开环，回 `Action` 就走闭环，服务端按场景装配的 World 类型自动选择会话形态。一个插件也可以两者都支持。

## 2.4 写一个 SUT：拆解真实代码

这是 `cicd_test` 的完整算法进程，40 行，我们逐段看。

```python
from autotest.protocol import messages as msg
from autotest.protocol.schema import decode_observation, encode_action
from autotest.registry import load_plugin
from autotest.sdk import SutBase

invp = load_plugin("ctrl.invp")          # ①

_DEFAULT_GAINS = {"kp": 30.0, "kd": 5.0, "kx": 1.0, "kxd": 2.0}


class PdPendulum(SutBase):               # ②
    """PD 状态反馈：F = kp·θ + kd·θ̇ + kx·x + kxd·ẋ（无内部状态，reset 无需清理）。"""

    module = "ctrl.invp"                 # ③

    def on_init(self, config):           # ④
        p = config.get("hyperparams", {})
        self._gains = {k: float(p.get(k, v)) for k, v in _DEFAULT_GAINS.items()}
        return super().on_init(config)

    def on_step(self, observation):      # ⑤
        obs = decode_observation(observation["data"])          # ⑤a → InvpObs
        g = self._gains
        force = (                                              # ⑤b ← 你的算法在这里
            g["kp"] * obs.theta + g["kd"] * obs.theta_dot
            + g["kx"] * obs.x + g["kxd"] * obs.x_dot
        )
        return msg.Action(                                     # ⑤c
            "ctrl.invp",
            encode_action("ctrl.invp.InvpAction", invp.InvpAction(force=force)),
        )


def main() -> None:                      # ⑥
    sut = PdPendulum("invp-sut")
    try:
        sut.spin()
    finally:
        sut.close()
```

### ① `load_plugin("ctrl.invp")`——为什么算法要加载插件

观测是跨进程传来的一串字节。要把它变成 `InvpObs` 对象，进程里得先注册好"`ctrl.invp.InvpObs` 这个 schema 该怎么解码"。`load_plugin` 干的就是这件事：**把插件的编解码器注册进当前进程**。不加载的话，`decode_observation` 会报"未知 schema"。

它返回插件模块对象，所以下面能直接用 `invp.InvpAction`。

> **这不算破坏黑盒吗？** 不算。你加载的是**数据格式定义**（相当于 protobuf 的 `.proto` 生成代码），不是判据、不是数据集、不是真值。插件里的 `checker.py` / `sim.py` 你既没 import 也用不上。

### ② 继承 `SutBase`

SDK 基类。会话建立、订阅发布、消息收发、帧循环**全部封装在里面**。你不碰任何网络代码。

（不想用 SDK？可以直接读环境变量 `AUTOTEST_SESSION` / `AUTOTEST_TOPICS` 用原生 tzcomm 实现协议，契约允许。ROS2 算法走 bridge 范式，模板见 [`examples/ros2_pipe_bridge.py`](../examples/ros2_pipe_bridge.py)。两条路都是少数情况，入门先用 SDK。）

### ③ `module = "ctrl.invp"`

声明自己属于哪个命名空间。它会出现在你发出的每条消息里，也是 `READY` 时的自报家门。

### ④ `on_init`——读超参

`config` 里有三样东西：

```python
{
  "sensor_config": {"lidar": {"front": "/points"}},   # 传感器实例 → topic（由本体资产生成）
  "hyperparams":   {"kp": 8.0},                       # 超参（manifest + 场景合并后的结果）
  "body_profile":  {...}                              # 本体 profile（外参等），无 body 引用时缺省
}
```

**注意这里的写法**：`p.get(k, v)`——超参**有默认值**，评测方没下发就用算法自己的默认。这是正确姿势。反面教材是把增益写死在代码里，那样测试工程师就没法做参数扫描了（§2.7）。

记得 `return super().on_init(config)`——基类的返回值就是 `READY` 报文（`module` / `version` / `required_sensors`）。

### ⑤ `on_step`——核心钩子

每帧调一次，三段式：

- **⑤a 解码**：`observation` 是外层信封 `{timestamp, module, data}`，`decode_observation(observation["data"])` 把数据面解出来，得到 `InvpObs` 对象（`x` / `x_dot` / `theta` / `theta_dot`）。字段定义查插件的 [contract.md](../plugins/ctrl.invp/contract.md)。
- **⑤b 推理**：**换成你的算法，只有这几行要改。** 这里是一行 PD 控制律。
- **⑤c 编码回传**：闭环回 `msg.Action(命名空间, 编码后的数据)`；开环回 `msg.Result(...)`。

**时钟提醒**：这个例子的 PD 控制律不需要时间。一旦你的算法要积分、要差分、要预测，时间**必须**取 `observation["timestamp"]`。

### ⑥ `spin()` / `close()`

进入帧循环，直到收到 `TERMINATE`。生命周期由 SDK 驱动。

### 没写的两个钩子

`PdPendulum` 没覆写 `on_reset` 和 `on_terminate`，因为 PD 控制器**无内部状态**——每一步的输出只取决于当前观测。有状态的算法必须覆写 `on_reset`：

```python
def on_reset(self, testcase_meta):
    """每个 testcase 前：清运行状态，保留模型。"""
    self._integral = 0.0            # 清：积分项
    self._prev_error = None         # 清：上一帧误差
    self._map.clear()               # 清：地图
    # self._model 不动 —— 模型/权重跨 testcase 复用

def on_terminate(self, reason):
    """可回自统计，进报告的 comm_health / 算法侧统计。"""
    return {"n_inferences": self._count}
```

## 2.5 开环版对照

把上面的例子换成开环（SLAM），差异只有两处。完整代码见 [`examples/slam_algo.py`](../examples/slam_algo.py)：

```python
def on_step(self, observation):
    data = decode_observation(observation["data"])       # → SlamData（多传感器容器 + 里程计）
    pose = data.odom if data.odom is not None else Pose(0, 0, 0, 0, 0, 0, 1)
    return msg.Result(                                   # ← 差异 1：Result 不是 Action
        "pipe.slam",
        encode_result(                                   # ← 差异 2：encode_result 不是 encode_action
            "pipe.slam.StampedPose",
            StampedPose(timestamp=observation["timestamp"], pose=pose),   # ← 时钟取观测时间戳
        ),
    )
```

**其余部分——基类、四个钩子、加载插件、manifest 写法——完全一样。** 这就是"一套协议两种模式"的意思。

**可跑的完整开环算例**：[`tz-Box/cicd_test_slam`](https://github.com/tz-Box/cicd_test_slam)
——回声 SLAM + 三档 benchmark，与本关的倒立摆（闭环）互补。开环这一路的
"真实本体 + 传感器声明 + 数据集回放"在那里都能看到实物：

```bash
git clone git@github.com:tz-Box/cicd_test_slam.git ~/ws/cicd_test_slam
python3 -m autotest.client run ~/ws/cicd_test_slam/scenario.yaml --json
```

与倒立摆算例的差别，恰好是开环相对闭环多出来的那几件事：

| | `cicd_test`（闭环） | `cicd_test_slam`（开环） |
|---|---|---|
| 回什么 | `Action`（力） | `Result`（位姿估计） |
| body | `invp_sim` 空壳台架，`sensors: {}` | `pbox_v1` 真实本体（lidar ×2 + imu + camera） |
| `required_sensors` | `{}`（不校验） | `{lidar: [front]}`，**握手时真的校验** |
| 数据从哪来 | 仿真器现算 | 数据源逐帧回放 |

补充两条开环特有的自由度（SDK 支持，但入门用不上）：一帧可以回多个 result；也可以攒若干帧一起回。结果是异步发出的，不受喂帧频率约束。

## 2.6 manifest：仓根的 `scenario.yaml`

这是你交付的第二样东西，回答"这个仓怎么被测"。

```yaml
launch: "python3 invp_sut.py"        # ★必填。启动命令，工作目录 = 本文件所在目录
consumes: ["ctrl.invp.InvpObs"]      # ★必填。我这个算法消费哪种观测 schema
required_sensors: {}                 # 我需要哪些传感器实例（纯仿真填 {}）
hyperparams: {}                      # 超参默认值，会经 INIT 下发
runtime: { type: host }              # 运行环境（缺省 host = 宿主机直跑）
scenarios:                           # ★场景清单：这个仓提供哪几套题
  - id: small_push                   #   id 必须是 ^[a-z0-9_]+$，清单内唯一
    description: 小扰动单点冒烟       #   给人看的说明（Hub 勾选界面显示它）
    scenario: scenarios/small_push.yaml
  - id: full
    description: 完整评测
    scenario: scenarios/sim_basic.yaml
```

**`consumes` 是干什么的**——这是本关最容易被忽略、但设计上最重要的一个字段。

装配一次评测时，框架会检查三方是否配套：

```
数据源声明它产出什么   produces = ["ctrl.invp.InvpObs"]
                              ⊇
判据声明它需要什么     consumes = ["ctrl.invp.InvpObs"]
你的算法声明它吃什么   consumes = ["ctrl.invp.InvpObs"]
```

不匹配就**立刻失败并明确报错**（fail fast），而不是让你跑完 10 分钟才发现算法收到的是一堆解不开的字节。这条规则把"算法 ↔ 数据 ↔ 判据"三者的归属关系拴在一起，靠的纯粹是命名空间约定，框架核心不认识任何具体算法。

**场景清单 vs 旧式单场景**：老仓可能写 `scenario: scenarios/xxx.yaml`（单个），仍然兼容，等价于一个匿名默认场景。新仓一律用 `scenarios:` 清单——Hub 的手动触发界面读的就是这个清单来给你勾选。字段全集见[附录 · scenario.yaml Schema](07-附录-scenario-yaml-schema.md)。

**依赖隔离**：算法有第三方依赖时，写 `runtime: { type: venv }` 并在仓根放 `requirements.txt`，评测机会建虚拟环境装依赖再跑。注意 **ATP SDK（autotest / tzcomm）由评测环境提供，不要写进你的 requirements.txt**。详见附录 §5。

## 2.7 超参：不要硬编码

超参有三层，**深合并**，后者覆盖前者：

```
manifest 的 hyperparams（算法默认）
        ▼ 被覆盖
场景文件的 hyperparams（这套题指定的参数）
        ▼ 被覆盖
场景清单项的 hyperparams（这个 benchmark 条目指定的参数）
```

第 1 关让评测变红时用的就是最外层：

```yaml
scenarios:
  - id: weak_gain
    scenario: scenarios/hard_push.yaml
    hyperparams: { kp: 8.0, kd: 1.0 }     # ← 覆盖算法内置的 kp=30, kd=5
```

**为什么这件事重要**：把参数暴露成超参，等于把"参数扫描"这个能力免费送给测试工程师——同一份算法代码、同一个世界、同一把尺子，只改参数就能生成一组 benchmark 条目，比较不同参数下的表现。硬编码在代码里就做不到了。

**什么该做超参**：控制增益、迭代次数、置信阈值、体素大小这类**调优旋钮**。
**什么不该**：算法结构、模型权重路径这类换了就等于换了个算法的东西——那应该走新会话（新的评测），而不是超参。

## 2.8 动手：把倒立摆换成你的算法

**如果平台已有你这类算法的插件**（`pipe.slam` / `nav2d` / `ctrl.invp` / `manip.force`），只要改 4 处：

| 改什么 | 改成 | 从哪查 |
|---|---|---|
| `load_plugin("...")` 和 `module` | 你的算法类型对应的命名空间 | `plugins/` 目录名 |
| `on_step` 里的推理代码 | 你的算法 | —— |
| `decode_observation` 得到的对象怎么用 | 你的输入字段 | 该插件的 `contract.md` §1 |
| `encode_result/action` 的类型名与字段 | 你的输出 | 该插件的 `contract.md` §1 |

再写 manifest，指向插件的预置场景（如 `plugins/ctrl.invp/scenarios/sim_basic.yaml` 的同款写法）先跑通，然后进[第 3 关](03-第3关-定义benchmark.md)定义自己的 benchmark。

**如果平台没有你这类算法**：你现在还没有可以对话的 World 和 schema。**先别急着造**——建议拿倒立摆做完练习（比如把 PD 换成 LQR，或者实现一个"先摆起再稳住"的能量控制器，看 `max_abs_theta` 和 `settle_error` 怎么变），有了完整体感再进[第 4 关](04-第4关-开发评测插件.md)设计自己的插件。

**接入时最常见的四个错误：**

| 症状 | 原因 |
|---|---|
| 启动就报"未知 schema" | 忘了 `load_plugin`，或者 `consumes` 写的 schema 名跟插件对不上 |
| 第 1 个 testcase 过、第 2 个开始崩 | `on_reset` 没清干净，状态残留 |
| 本地能跑，`--clock-rate 2.0` 就不对 | 算法读了墙上时钟 |
| 装配期直接 fail fast | `consumes` / `required_sensors` / `body` 三者声明不一致，报错会直指缺失项 |

## 2.9 本地调试三件套

**① 本机跑一次完整评测**（不走 HTTP 服务，最快的迭代方式）

```bash
python3 -m autotest.client run <你的仓>/scenario.yaml [--scenario <场景文件>] [--clock-rate 1.0] [--json]
```

`--clock-rate`：`1.0` 按原始帧间隔实时复现（默认）；`2.0` 加速一倍；`0` 全速（只适合冒烟）。

**② 暂停 / 单步**——评测跑到一半想 attach 调试器、打印中间量：

```bash
python3 -m autotest.client pause  <job_id>       # 世界冻结：停喂帧，时钟停住，算法安全等待（不会超时判死）
python3 -m autotest.client step   <job_id> -n 10 # 暂停中单步放行 10 帧
python3 -m autotest.client resume <job_id>       # 恢复
```

**③ 通信链路自检**——怀疑不是自己的问题时，先排除底层：

```bash
python3 -m autotest.commcheck        # daemon 可达 / 订阅发布回环 / 服务回环，退出码 0/1
TZCOMM_LOG_LEVEL=DEBUG python3 ...   # 打开底层通信诊断日志
```

另外，每份报告都带 `comm_health`，**服务端和算法端各自统计收发帧数与丢包**。如果 `warnings` 非空（双侧丢包率超 1%），那多半不是你的算法问题，把报告发给通信负责人。完整归因表见[速查手册](06-速查手册.md)。
