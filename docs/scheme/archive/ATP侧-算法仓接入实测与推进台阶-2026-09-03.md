# ATP 侧 · 算法仓接入的实测现状与推进台阶（2026-09-03）

> 背景：本文不谈契约设计，也不谈协作机制——那两块分别由
> [《四平台协同推进的体系性缺口与建议》](ATP侧-四平台协同推进缺口分析-2026-09-02.md)
> 与[《三平台打通推进计划》](PatrolBox-三平台打通-推进计划.md)覆盖。
>
> 本文只回答一个问题：**真实算法仓要接进来，现在还差什么，按什么顺序做。**
>
> 判断依据全部来自三边数据库直读（ATP `artifacts/atp.db`、Hub `data/hub.db`、
> PMS `data/local.db`，区间 2026-08-18 ~ 2026-09-02）与代码实读，不是推演。

## 0. 一句话诊断

> **能力建了很多，只跑通过一条：ATP 有史以来的全部 16 次评测，都是倒立摆。**

`pipe.slam`（4 种数据源 + 2 个 checker）、`nav2d`、`manip.force` 三个插件族在服务端
**一次都没执行过**；ROS2 桥接从未跑过；`data/pipe-real` 不存在。

这不是说能力白建了——恰恰相反，它们是接入真实算法的前提。但它意味着：
**每接一个新算法域，都是在给对应插件族做首次真机验证**，而首次验证必然会暴露问题。
推进节奏应当据此设计，而不是假设「插件写好了就能用」。

## 2. 决策记录（2026-09-02 与 M 讨论确认）

### 决策 1 · tzcomm 不走 ATP 评测通路

曾考虑用 tzcomm 作为「接入复杂度」的验证载体。**否决**，三条独立理由：

1. **循环依赖（决定性）**：tzcomm 是 ATP 的传输底座——`pyproject.toml` 写着
   「统一自动化测试服务框架（**基于 tzcomm**）」，`commcheck.py` / `sdk/sut.py` /
   `eval/runner.py` / `eval/closed_loop.py` / `server/runtime.py` / `server/http.py`
   六个核心模块全部 import 它，`/atp/health` 直接报 `"tzcomm": true`。
   **用依赖 X 的框架去测 X**：tzcomm 真出问题时 ATP 自己起不来，报不出「tzcomm 测试失败」，
   只会报「ATP 挂了」——最需要它工作的时候恰恰是它失效的时候。
2. **已有更合适的 CI**：tzcomm 有 19 个 pytest 文件（subpub / service / action / 分片 /
   端口重绑 / 竞态 / 丢包统计…）+ 完整 GitHub Actions（Python 3.9/3.10/3.12 矩阵 + Redis service）。
   契约 §2 本就把这类归为「不在本契约范围」。
3. **语义错配**：ATP 的评测模型是「body + dataset → SUT 消费 observation 产生 action →
   checker 判定指标」。tzcomm 关心吞吐 / 丢包 / 端口重绑 / 多进程竞态，
   **没有 body、没有 observation、没有指标阈值**。硬套要凭空造「通信本体」和「通信 checker」，
   那是为了用工具而造需求。

> 附带澄清：`body: invp_sim` 其实是空壳（`urdf_path: ""`、`sensors: {}`），
> 所以「必须是机器人」不是门槛。门槛是「必须是消费观测、产生动作、可用指标判定的东西」。

### 决策 2 · ROS2 桥归 tzcomm 生态，不归 ATP

M 的判断：桥应建在 tzcomm 上，这样 ATP 更轻，且所有 tzcomm 生态成员
（算法仓、pbox-simulator）都能享受 ROS2 互通。**采纳，且 tzcomm 已完成一半。**

tzcomm 现有两个桥（`bridge/`）：

| | `ros2_dds` | `ros2_topic_bridge` |
|---|---|---|
| 截取层 | RTPS/DDS（绕过 rcl，裸 CycloneDDS） | ROS 层（rclpy 正常订阅） |
| 依赖 | 仅 CycloneDDS，**不装 ROS2 也能用** | 整个 rclpy（需 ROS2 环境） |
| 接新话题 | 写 IDL + converter + config（三步） | **只改 config.yaml 一条**（`__slots__` 反射） |
| 已覆盖类型 | PointCloud2、Imu | 任意 |
| 代码量 | 166 行 | 160 行 |
| 自带测试 | 无 | `test_bridge.py` 175 行 |

其 README 的定位与 M 的设想一致：「作为 tzcomm 的一个**独立业务进程**，
不是 tzcomm 的新 transport、也不改守护进程……下游业务节点完全无感」。

**但缺关键的另一半：两个桥都是 ROS2 → tzcomm 单向（订阅 ROS 话题转发到 tzcomm），
没有 tzcomm → ROS2 的发布方向。** 而 ATP 评测是双向的：

```
ATP dataset(tzcomm) ──观测──> ROS2 算法      ← 需要 tzcomm → ROS2  ❌ 缺失
ROS2 算法 ──结果──> ATP checker(tzcomm)      ← 需要 ROS2 → tzcomm  ✅ 已有
```

### 决策 3 · ATP 的 `ros2_pipe_bridge.py` 应拆薄

现有 260 行做了两件事，**只有一件该留在 ATP**：

```
现状：ATP ──[260 行：ATP 协议握手 + ROS 话题转换 全包]──> ROS2 算法

目标：ATP ──[~80 行：只做 ATP 协议握手]──> tzcomm topic ──[tzcomm 桥，现成]──> ROS2 算法
```

ATP 协议部分（INIT/READY/RESET/STEP/RESULT/TERMINATE/FINAL 状态机 +
`AUTOTEST_SESSION`/`AUTOTEST_TOPICS` 注入 + observation 信封解码）是 ATP 特有的，删不掉；
ROS 话题转换正是 tzcomm 桥的活。

**拆完后算法仓要写的代码从 260 行降到约 80 行，且那 80 行对所有 ROS2 算法长得一样，可做成模板。**

> 参考量级：纯 tzcomm 的 SUT 适配只要 39~54 行
> （`nav_sut.py` 39、`slam_algo.py` 41、`invp_sut.py` 51、`manip_sut.py` 54）。

### 决策 4 · 验证载体用新仓 `cicd_test_slam`，不做机械臂样例

曾考虑加机械臂（`manip.force`）样例作为 slam/nav 的铺垫。**改为直接做简单 SLAM**，理由：

| | 倒立摆（已跑通） | 机械臂（曾提议） | SLAM/Nav（真实目标） |
|---|---|---|---|
| body | `invp_sim` 空壳 | `manip_sim` 空壳 | `pbox_v1` 真实本体 |
| 传感器 | `{}` | `{}` | `{lidar: [front, rear]}` |
| 数据源 | 合成（sim.py 现算） | 合成（sim.py 现算） | rosbag 回放 + GT 文件 |
| 判定 | 现成阈值 | 现成阈值 | 真实数据下需标定基线 |
| SUT | 51 行 | 54 行 | ROS2 桥接 |

**机械臂与倒立摆结构完全同构**——做它等于第二次走同一条路，
碰不到 slam/nav 的任何一个真实难点（真实数据、传感器声明、GT 标定、ROS2 桥接、重量级 runtime）。

> 机械臂样例仍有一个正当用途：**验证文档**——让另一位算法工程师照着
> [第 2 关](../../02-第2关-接入你的算法.md) 独立走一遍，检验教程是否够用。
> 那是「验证文档」，不是「给 slam/nav 铺垫」，两个目标不要混。

**不在 `cicd_test` 里加**：它现在是 Hub→ATP 全链路的健康基线（16 次评测全绿），
价值在于**稳定**；往里加东西会让「基线绿不绿」这个信号变浑浊。

## 3. 推进台阶

设计原则：**每一级只引入一个新变量，前一级不过不进下一级。**
这样失败时归因唯一——不会出现「指标不达标，但分不清是算法、数据还是阈值的问题」。

### S0 · tzcomm 补 `tzcomm → ROS2` 发布方向 ★

**归属**：tzcomm（非 ATP）。**可与 S1 并行，不阻塞 S1。**

- 优先做 `ros2_topic_bridge` 而非 `ros2_dds`：算法仓本来就有 ROS2 环境，
  反射方式接任意话题**零类型代码**；`ros2_dds` 每种消息都要手写 IDL + converter。
- 配置形态建议：现有 `bridges[]` 每条加 `direction: sub | pub`（缺省 `sub`，向后兼容）。
- **这是当前唯一在关键路径上、且完全不存在的东西。**
- 价值不止 ATP：补完之后 pbox-simulator（若为 tzcomm 侧）可直接驱动 ROS2 算法。

**验收**：ROS2 侧能订阅到由 tzcomm 发布的 PointCloud2 / Imu；`test_bridge.py` 覆盖双向。

### S1 · `cicd_test_slam` + 合成数据跑通

**新变量：`pipe.slam` 插件族首次在服务端执行。**

- 内容：`examples/slam_algo.py`（41 行回声 SLAM）+ `scenarios/synthetic_slam.yaml`
  （`pipe.slam.synthetic` 数据源、`pipe.slam.ape` checker、ate/rpe 阈值）
- 走完整六步接入：GitHub App → 仓内 manifest → Hub 侧配置 → ATP 跑通 →
  PMS 绑项目 → PMS 绑任务
- **顺带把「第二个仓接入要多久」量出来**——不需要再单独做接入探针仓

**验收**：ATP 产出 ate/rpe 指标，结果经 Hub 回到 PMS 任务卡的「CI 结果」区块。
**同时记录每步耗时与卡点**——这决定了后续是「该排期指派」还是「该降低接入成本」。

### S2 · 接 pbox-simulator

**新变量：闭环 + 真实仿真器（GT 仍精确）。**

ATP 的 `IWorld` 抽象已就绪，接入 = 实现一个子类，五个方法：

```python
class PboxSimWorld(IWorld):
    closed_loop = True                    # step 消费 action 推进
    produces = ["pipe.slam.SlamObs"]
    def testcases(self) -> list[str]: ...
    def reset(self, testcase_id) -> dict: ...          # 首帧观测信封
    def step(self, action) -> tuple[dict | None, bool, dict]: ...
    def get_ground_truth(self) -> dict: ...            # 仿真优势：GT 精确
```

`plugins/nav2d/sim.py` 是现成的闭环 World 参考实现。

**验收**：同一个 SUT 不改代码，换 World 即可跑。

> **不建议 dataset 与 simulator 两条通路同步验证。** 两者 GT 来源根本不同
> （仿真是精确真值，rosbag 是标注文件），阈值标定方法也不同；同时上会分不清
> 「指标不达标」是算法、数据还是阈值的问题。**先 simulator（失败原因唯一），再 rosbag。**

### S3 · 真实 rosbag 数据

**新变量：真实数据 + 标注 GT + 多 lidar 时间戳对齐 + 阈值标定。**

- 采数据 → 配 `pipe.slam.rosbag`（`root` / `topic_map` / `gt_dir` / `max_frames`）
- `data/pipe-real` 当前不存在，需要先采集
- **这一级最可能卡住，也最值得提前撞**

**验收**：`scenarios/pipe_real.yaml` 跑通，`pipe.slam.pipe` checker
（`center_tolerance` / `direction_tolerance_deg`）给出可解释的判定。

### S4 · ROS2 算法端到端

**依赖 S0 + S3 均通过。新变量：真实 ROS2 算法。**

- 用拆薄后的 ATP 协议适配（~80 行）+ tzcomm 桥，接一个真实 ROS2 SLAM
- **本级的产出是一句话，比任何指标都重要：**

> **SLAM / Nav 不需要迁到 tzcomm。写约 80 行 ATP 协议适配 + 配一个 tzcomm ROS2 桥即可，
> 算法本身与内部通信一行不改。**

如果 S4 跑不通，才需要认真讨论通信层迁移——**但那是大得多的决定，
不该在验证之前就假设要做。**

## 4. benchmark 怎么写（给算法工程师的口径）

M 提出的问题：不同算法的 benchmark 不同，像 scenario 一样需要各自定义——那具体怎么写？

ATP 里 benchmark **不是一个数字，是三件事的组合**，且分属不同文件：

| 要素 | 在哪 | 形态 | 谁写 |
|---|---|---|---|
| **考什么工况** | 场景文件 `dataset.config.testcases` | yaml | 测试 / 算法工程师 |
| **怎么算指标** | checker 插件 `evaluate()` | **Python 代码** | 算法工程师 |
| **及格线画在哪** | 场景文件 `checker_config` / 清单项覆盖 | yaml | 测试工程师 |

关键提示（教程 [第 3 关](../../03-第3关-定义benchmark.md) 已详述，此处只标要点）：

- **checker 是代码不是配置**——这点要对算法工程师说清楚，别以为写 yaml 就够。
  接口是 `IChecker.evaluate(records, ground_truth, config) -> Score`。
- 一份场景文件可经清单项的 `hyperparams` / `checker_config` 深合并**生成多个 benchmark**
  （分级：PR 快速冒烟 vs 完整评测）。
- ⚠ **回归比较假设「指标越小越好」**——设计 metric 时要注意方向。
- ⚠ **深合并不能删键**——只能覆盖，不能移除。

## 5. 与代码上传的解耦（重要）

S4 的那句话是解除算法工程师心理负担最有效的东西，但它要等 S0 + S3 都通过，可能数周。

**建议不要等。** 现在就推进代码上传，并明确告知：**通信层先不动。**

理由：

1. 代码上传与通信层改造**本就可以解耦**；
2. 当前 S/N1/N2/O 四人 81 个任务完成 0 个，**代码不上传，后面所有验证都是空转**；
3. 代码上传后 Hub 的 events 立刻能看到真实活动，PMS 的交付健康度也能反映真实进度；
4. S0~S3 的验证**完全不需要真实算法代码**（用 41 行回声 SLAM 即可），两条线天然并行。

| | **S4** ROS2 算法端到端（含 `ros2_pipe_bridge` 拆薄） | ATP + tzcomm | — |
