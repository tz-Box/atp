# ATP 侧 · 四平台协同推进的体系性缺口与建议（2026-09-02）

> 背景：PatrolBox 体系从三平台（PMS / Hub / ATP）扩到四平台（+ ARS）。
> 本文不谈任何单个系统的功能，只谈**"四个系统靠一份契约并行开发"这个协作机制本身**还缺什么。
> 判断依据：接口面数量从 2 条（Hub↔ATP、Hub↔PMS）增到 4 条，
> **靠人读文档保持对齐的成本是超线性增长的，而现在的机制全部是"人读 + M 批准"。**

---

## 0. 一句话诊断

> **现在这套体系的契约是"文档"，不是"会红的东西"。**

四个系统之间没有任何一处自动化机制能在接口被改坏时报警。
唯一的对齐手段是「人读 988 行契约 + M 批准 + 通知三方 owner」。
三个系统时这还能撑住；四个系统、六条接口面之后，它会以**静默失配**的形式失效——
不是有人报错，而是某天发现某个字段三个月前就没人填了。

下面 7 个缺口按 **价值 / 成本** 比排序，前 4 个建议尽快做。

---

## 缺口 1 ★ 契约没有可执行形态（无 contract test）

**现状**：§4 定义了十几个跨系统报文，全部只以 Markdown 代码块存在。
各系统自己写自己的 Pydantic model / dict 组装，**没有任何共享的事实源**。

**会怎么坏**：ARS 回调时 `report.metrics` 少填一个键、Hub 透传 `context` 时结构变了、
PMS 某次重构改了 `/pms/ci-results` 的容忍度——这些都不会有任何系统报错，
会一直沉默到某个展示层显示空白，然后花半天查是谁的锅。

**建议（成本 2–3 天，一次性）**：

1. 在 **PMS 仓 `schema/` 下**（契约唯一事实源所在地）新增 `schema/contracts/`：
   ```
   schema/contracts/
   ├── ci_callback.schema.json          # POST /api/ci/callback
   ├── pms_ci_results.schema.json       # POST /pms/ci-results
   ├── atp_evaluations_submit.schema.json
   ├── ars_reviews_submit.schema.json
   ├── report_metrics.autotest.schema.json
   ├── report_metrics.aireview.schema.json
   └── fixtures/                        # 每个报文 2–3 个真实样例（含边界：字段缺失、advisory、timeout）
   ```
2. 每个系统在自己 CI 里加**两个方向**的测试：
   - **出向**：我实际发出的报文能过对方的 schema；
   - **入向**：`fixtures/` 里的每个样例我都能解析且不崩（含未知 check_type、缺失可选字段）。
3. schema 文件的变更**就是**契约变更，走同一套 M 批准纪律。

**收益**：契约从"大家都读过的文档"变成"改坏了 CI 会红的东西"。
且入向测试天然覆盖了[评审意见 #4](ATP侧-总契约v1.7评审意见-2026-09-02.md)
要求的"未知 check_type 不得报错"——**规则有了执行力**。

> 这是本文唯一一条我认为"应该在 v1.7 批准的同时启动"的。四个系统之后再补，成本只会更高。

## 缺口 2 ★ 只有组件级探活，没有链路级探活

**现状**：`/atp/health`、`/ars/health`、Hub 探活四件套齐全。
但**四个组件全绿，链路仍然可能是断的**——Hub 的 GitHub App token 过期、
PMS 端点悄悄改了字段容忍度、回调 token 轮换后有一方没同步、
webhook 订阅少了一个 action……这些都不会让任何 health 变红。

**发现时机**：下一次有人手动测试的时候。四方并行开发时，这个间隔可能是好几天。

**建议（成本 1–2 天）**：**合成 PR 金丝雀**。

在 `cicd_test` 仓（现成的算例仓，已有真实 manifest 与场景）上挂一个每日定时任务：

```
每天 03:00
  ├─ 在 cicd_test 开一个 PR（改一行注释）
  ├─ 等待 autotest + aireview 两条 check 回来（超时 30 min）
  ├─ 逐项断言：
  │    ① Hub 收到 webhook 并生成了 cid
  │    ② ATP 回调归位、ARS 回调归位
  │    ③ GitHub check-run 两条都写上了（autotest=success / aireview=neutral）
  │    ④ PMS 任务卡收到了 ci-results（按 cid 查得到）
  │    ⑤ 各步耗时在基线范围内
  ├─ 关闭 PR、清理
  └─ 任一断言失败 → ci_alert（§4.4，无归位目标的基础设施告警）
```

**为什么放在 cicd_test 而不是新建仓**：它已经是全链路联调用的仓，
有真实 manifest、真实场景、已注册 Hub 路由、已配 deploy key——**零额外配置**。

**收益**：这是四平台**唯一的活体健康检查**，也是唯一能在"没人动它"的时候
发现链路退化的机制。同时它顺手成了 v1.7 上线的验收脚本。

## 缺口 3 ★ 没有 cid 的全链路可观测性

**现状**：cid 贯穿四个系统，但追一次问题要分别登 Hub console、
翻 ATP 的 `artifacts/<job_id>/session.log`、开 ARS 审查页、查 PMS 任务卡。
**没有任何一处能回答"这个 cid 现在在哪、卡在哪一步、每步花了多久"。**

**关键观察**：**Hub 已经有全部数据了**——它生成 cid、落 pending、调度、
收回调、写 check-run、推 PMS，每一步都经过它。缺的只是把这条时间线画出来。

**建议（成本 1–2 天，纯 Hub 侧，无跨系统改动）**：Hub console 加一个 cid 追踪页：

```
cid: chk_01J8X...        repo: tz-Box/cicd_test    sha: a1b2c3d    check_type: aireview
──────────────────────────────────────────────────────────────────────────────────
✅ 14:30:02  webhook 收到          pull_request:opened        delivery=abc123
✅ 14:30:02  pending 落库          pms_task_id=rec_xxx  (来自 /pms/lookup)
✅ 14:30:03  context 取得          PMS 200,  2 tasks / 1 deliverable      (+0.4s)
✅ 14:30:03  submit → ARS          202  review_id=rev-8f3a  units_planned=12
⏳ 14:33:41  回调未达               已轮询 3 次，下次 14:34:11，超时 14:50:03
⬜ ——        check-run 回写
⬜ ——        PMS 推送
```

**收益**：排障从"跨四个系统翻日志"变成"打开一个页面"。
这也是把 Hub 的**编排者**身份兑现成运维价值的地方——现在 Hub 承担了编排职责，
却没有承担编排的可观测性。

## 缺口 4 ★ 契约版本与实现版本无法对账

**现状**：契约是 v1.7，但**四个运行中的系统各自实现到哪个契约版本，没有任何地方能查**。
`/atp/health` 返回的 `version` 是**包版本**（`0.1.0`），不是契约版本。

**会怎么坏**：四方并行开发时，「我以为对方已经升到 v1.7 了」是最高频的失配来源。
表现是某个新字段一直是空的，而两边都以为是对方的问题。

**建议（成本：每个系统 1 小时）**：

1. 所有 health 端点增 `contract` 字段：
   ```json
   {"ok": true, "version": "0.1.0", "contract": "1.7", "tzcomm": true, "queue": 0}
   ```
   （PMS 无 health 端点则在其现有状态端点上加，或新增 `GET /pms/health`。）
2. Hub 探活时记录，console 显示一张**契约版本矩阵**：

   | 系统 | 实现契约版本 | 契约当前版本 | 状态 |
   |---|---|---|---|
   | Hub | 1.7 | 1.7 | ✅ |
   | ATP | 1.7 | 1.7 | ✅ |
   | ARS | 1.7 | 1.7 | ✅ |
   | PMS | **1.6** | 1.7 | ⚠️ 落后一版 |

3. 契约里加一条纪律：**实现某版本的全部己方条款后，才允许把 `contract` 提到该版本。**

**这是全文成本最低、见效最快的一条。** 强烈建议随 v1.7 一起落。

## 缺口 5 「执行体接入」没有沉淀成可复用规范，Hub 侧正在走向复制粘贴

**现状**：ARS 是第二个执行体，它的接口面是"照抄 ATP"，
而这个"照抄"是靠人读 ATP 就绪公告完成的。契约 §8.2 明确写着
「`ars_pool` 模块——**复制 ATP 池化模块**」。

**复制是技术债的开始。** 第三个执行体（性能压测 / 静态分析 / 文档一致性检查 / 安全扫描——
都是自然的下一步）会再抄一遍，而 Hub 侧会有三份几乎相同的 `*_pool.py`。

**建议（成本 2–3 天，现在正是最佳时机）**：

1. **契约层**：把 §4.8 / §4.9 的共同部分抽成 **§4.X「执行体通用接口规范」**：
   submit / status / health / callback 四件套、Bearer 认证、cid 幂等、
   坐标类错误 4xx 快失败、回调重试 1s/5s/15s、池化探活与路由跳过、`ci_alert` 切分。

   §4.8 / §4.9 退化为**只写差异**的一张表：

   | 维度 | autotest (ATP) | aireview (ARS) |
   |---|---|---|
   | 端口 | 2335 | 2336 |
   | submit 领域字段 | `scenario` / `save_baseline` | `pr{}` / `profile` / `scope` / `context` |
   | 并发模型 | 单机串行 | 可并发（默认 3） |
   | 超时 | 60 min | 20 min |
   | conclusion 语义 | 业务成败 | 恒 success（除自身失败） |
   | check-run conclusion | success/failure | 恒 neutral |
   | `report.metrics` | 可选（建议补，见评审 #10） | 必填 |
   | 详情页 | Hub console | ARS 自建 + Hub 跳板 |

2. **Hub 实现层**：`atp_pool.py` + `ars_pool.py` 合并为**配置驱动的 `executor_pool.py`**，
   执行体清单进 `config.json`。第三个执行体的接入成本从"抄一个模块"降到"填一段配置"。

**为什么是现在**：有两个实例了，抽象**有依据**（一个实例做抽象是臆测）；
还没有第三个，改动**成本最低**。**这个窗口过了就是三份复制。**

## 缺口 6 降级矩阵不对称：只有 ARS 有

§4.9.7 给了一张很好的「ARS 各种失败时全链路怎么办」的矩阵。
**但 ATP / PMS / Hub 自身不可用时的降级语义，契约里是散落的、不完整的。**

具体没答案的问题：

- **ATP 重启 30 秒**时 Hub 的 pending check 会怎样？（有重试吗？还是直接判 failure？）
- **PMS 不可用**时 Hub 的 ci-results push 会怎样？有 outbox 吗？丢了怎么办？
  （PMS 侧有 outbox 机制，但那是 PMS→飞书方向；Hub→PMS 方向的可靠性契约里没写。）
- **Hub 重启**时正在 running 的 ATP/ARS 作业怎么归位？（§8.2 说"pending/cid 状态持久化，重启不丢"，
  但没说重启后是否会重新轮询已 running 的作业。）

**建议（成本：半天，纯文档）**：把 §4.9.7 那张表**推广成 §X 全系统降级矩阵**，
四个系统各一行 × 若干失败模式。ARS 那张表的质量很高，直接作为模板。

**为什么重要**：这是**生产就绪**问题，不是设计洁癖。
四个系统意味着任意时刻有一个在重启/发版的概率翻倍了。

## 缺口 7 缺一份"体系导览"，新人无入口

**现状**：ATP 有五关教程，Hub 有技术路径文档，PMS 有 README + AGENTS.md，ARS 有 README。
**但没有一份文档回答"这四个系统是什么关系、我该读哪几份"。**

总契约 §1 那张职责边界表其实就是答案，**但它埋在一份 988 行的契约里，
而契约是给 owner 读的，不是给新人读的**。

**建议（成本 1 小时）**：在 PMS 仓（契约事实源所在地）放一份两页纸的
《PatrolBox 工程体系导览》：

- 四个系统各一句话 + 一张数据流图（可直接取 §2 部署拓扑）
- **按角色的阅读路径**：
  | 你是 | 先读 | 再读 |
  |---|---|---|
  | 算法工程师 | ATP 五关教程 | 用到 CI 时读第 5 关即可 |
  | 后端/平台开发 | 本导览 → 总契约 §1/§2/§3 | 自己系统的子契约 |
  | 测试工程师 | ATP 第 3、4 关 | ARS 评审规则集 |
  | 新 owner | 总契约全文 + 自己系统的推进计划 | —— |
- 一句话说明**总契约在哪、谁能改、怎么改**（变更纪律）

## 优先级汇总

| # | 缺口 | 成本 | 建议时机 | 归属 |
|---|---|---|---|---|
| **4** | health 带 `contract` 版本 + Hub 版本矩阵 | 1 h / 系统 | **随 v1.7 一起** | 四方各自 + Hub 汇总 |
| **1** | 契约 JSON Schema + fixtures + 双向 CI 校验 | 2–3 d | **v1.7 批准即启动** | 契约事实源在 PMS 仓；各系统各自接 CI |
| **3** | Hub cid 全链路追踪页 | 1–2 d | v1.7 期间 | Hub（数据已有，无跨系统改动） |
| **2** | 合成 PR 金丝雀（链路级探活） | 1–2 d | **v1.7 上线时**（顺手就是验收脚本） | Hub 起定时器；断言逻辑可放 cicd_test |
| **5** | 执行体通用接口规范 + `executor_pool` 合并 | 2–3 d | **v1.7 定稿前**（窗口期） | 契约：M / 实现：Hub |
| **6** | 全系统降级矩阵 | 0.5 d | v1.7 定稿前 | M + 四方各填一行 |
| **7** | 体系导览两页纸 | 1 h | 随时 | 建议 M 或 PMS owner |

**如果只做三件**：**#4（版本对账）→ #1（契约可执行）→ #2（链路探活）**。
这三件把"靠人对齐"换成"机器对齐"，是四平台规模下唯一可持续的协作方式。
