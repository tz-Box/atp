## 3. S · 算法仓接入台阶（主线）

**设计原则：每一级只引入一个新变量，前一级不过不进下一级。** 这样失败时归因唯一——
不会出现「指标不达标，但分不清是算法、数据还是阈值的问题」。

| # | 台阶 | 新变量 | 归属 | 阻塞 | 状态 |
|---|---|---|---|---|---|
| **S0** | tzcomm 补 `tzcomm → ROS2` **发布方向** | — | **tzcomm**（非 ATP） | 阻塞 S4 | 待做，可与 S1 并行 |
| **S1** | 新仓 `cicd_test_slam` + 合成数据跑通 | `pipe.slam` 插件族**首次服务端执行** | ATP + Hub + PMS | 阻塞 S2 | **仓内容已完成**（`cicd_test_slam@1927001`，三档实测通过）；⛔ 端到端待生产 tzcomm daemon 修复 + Hub 侧配置 |
| **S2** | 接 `pbox-simulator` | 闭环 + 真实仿真器（GT 仍精确） | ATP + simulator | 阻塞 S3 | 待做 |
| **S3** | 真实 rosbag 数据 | 真实数据 + 标注 GT + 多 lidar 对齐 + 阈值标定 | ATP + 数据采集 | 阻塞 S4 | 待做 |
| **S4** | ROS2 算法端到端（含 `ros2_pipe_bridge` 拆薄） | 真实 ROS2 算法 | ATP + tzcomm | — | 待做 |

### S0 · tzcomm 补发布方向 ★

tzcomm 现有两个桥（`bridge/ros2_dds`、`bridge/ros2_topic_bridge`）都是 **ROS2 → tzcomm 单向**，
而 ATP 评测是双向的：

```
ATP dataset(tzcomm) ──观测──▶ ROS2 算法      需要 tzcomm → ROS2   ❌ 缺失
ROS2 算法 ──结果──▶ ATP checker(tzcomm)      需要 ROS2 → tzcomm   ✅ 已有
```

**这是当前唯一在关键路径上、且完全不存在的东西。** 优先做 `ros2_topic_bridge`
（反射方式接任意话题零类型代码；`ros2_dds` 每种消息要手写 IDL + converter）。
配置形态建议：`bridges[]` 每条加 `direction: sub | pub`（缺省 `sub`，向后兼容）。

**验收**：ROS2 侧能订阅到由 tzcomm 发布的 PointCloud2 / Imu；`test_bridge.py` 覆盖双向。

### S1 · `cicd_test_slam` 合成数据跑通 ★

- 内容：`examples/slam_algo.py`（41 行回声 SLAM）+ `scenarios/synthetic_slam.yaml`
  （`pipe.slam.synthetic` 数据源、`pipe.slam.ape` checker、ate/rpe 阈值）
- 走完整六步接入：GitHub App → 仓内 manifest → Hub 侧配置 → ATP 跑通 → PMS 绑项目 → PMS 绑任务
- **顺带把「第二个仓接入要多久」量出来**，并记录每步耗时与卡点

**⚠ 前置 = D1（基线隔离）**：见 §4，不修则 S1 一跑就污染 `cicd_test` 的健康基线。

**不在 `cicd_test` 里加**：它现在是 Hub→ATP 全链路的健康基线（16 次评测全绿），价值在于**稳定**；
往里加东西会让「基线绿不绿」这个信号变浑浊。

**验收**：ATP 产出 ate/rpe 指标，结果经 Hub 回到 PMS 任务卡「CI 结果」区块。

### S2 · 接 pbox-simulator

`IWorld` 抽象已就绪，接入 = 实现一个子类五个方法（`plugins/nav2d/sim.py` 是现成的闭环参考）。

> **不建议 dataset 与 simulator 两条通路同步验证。** 两者 GT 来源根本不同（仿真是精确真值，
> rosbag 是标注文件），阈值标定方法也不同；同时上会分不清「指标不达标」是算法、数据还是阈值。
> **先 simulator（失败原因唯一），再 rosbag。**

**验收**：同一个 SUT 不改代码，换 World 即可跑。

### S3 · 真实 rosbag

配 `pipe.slam.rosbag`（`root` / `topic_map` / `gt_dir` / `max_frames`）；`data/pipe-real` 当前不存在，需先采集。
**这一级最可能卡住，也最值得提前撞。**

**验收**：`scenarios/pipe_real.yaml` 跑通，`pipe.slam.pipe` checker 给出可解释的判定。

### S4 · ROS2 算法端到端

依赖 S0 + S3。把 `examples/ros2_pipe_bridge.py` 从 260 行拆薄到约 80 行（**只留 ATP 协议握手**，
ROS 话题转换交给 tzcomm 桥）。**本级产出是一句话，比任何指标都重要：**

> **SLAM / Nav 不需要迁到 tzcomm。写约 80 行 ATP 协议适配 + 配一个 tzcomm ROS2 桥即可，
> 算法本身与内部通信一行不改。**

S4 跑不通，才需要认真讨论通信层迁移——**那是大得多的决定，不该在验证之前就假设要做。**

### ⚠ 与代码上传解耦（重要）

S4 那句话是解除算法工程师心理负担最有效的东西，但要等 S0 + S3，可能数周。**不要等**——
现在就推进算法仓代码上传并明确告知「**通信层先不动**」。S0~S3 的验证完全不需要真实算法代码
（41 行回声 SLAM 即可），两条线天然并行。

## 4. D · 线上缺陷收口（已验证，非推演）

| # | 缺陷 | 成本 | 状态 |
|---|---|---|---|
| **D1** ★ | **滚动基线是全局单文件 → 多算法仓接入即静默失效** | 0.5–1 d | **已完成** 2026-09-03（`4709a14`；+3 回归测试；现有基线已迁移） |
| **D2** | **无 job 级超时 → 单 job 卡死/超长即整条串行队列饿死** | 1–2 d | 待做 |

### D1 · 基线全局单文件

```python
# server/callback.py:59  读
baseline = load_baseline(artifacts_root() / "baseline.json")
# server/report.py:83    写
target = baseline_path or report_dir.parent / "baseline.json"   # = artifacts/baseline.json
```

整台 ATP **只有一份 `artifacts/baseline.json`**，不按 repo 分。而总契约 §4.8 明确 repo↔ATP 一对多。
于是 repo A 与 repo B 会互相覆盖基线，双方回归对比同时退化成永久 `vs_baseline: new=N`。

**最恶劣之处：它伪装成一个已知的良性现象。** 批次 F 收口记录写过「多场景前缀改变 testcase_id
命名空间，存量基线首轮全记 new（**一次性**，正常）」——症状一模一样，所以真 bug 发生时没人会查。

**为什么是 S1 的前置**：S1 接入的 `cicd_test_slam` 就是第二个仓。不先修，S1 一跑就污染
`cicd_test` 这条「16 次全绿」的健康基线，**而那条基线正是判断链路好坏的唯一信号**。

**修法**：基线按 repo 分文件（`artifacts/baselines/<owner>__<repo>.json`），旧全局文件作废重建。

### D2 · 无 job 级超时

`src/autotest/server/` 全量超时只有握手 10s、结果收集 30s、git 网络、pip 600s，**无 job 级上限**，
而 worker 是单线程串行。Hub 侧 60 分钟超时扫描已在产（v1.5）——超时后 Hub 判 `timeout` 归位，
**ATP 这边还在跑、还占着队列**，两边状态永久分叉，后续评测全部饿死且外部看不出来。

**不需要 bug 就能触发**：50000 帧 @ `dt=0.1`、`clock_rate=1.0` 的回放 = 83 分钟，合法超窗。
S3 真实 rosbag 正是这个量级。

**配套第二半**：running 态状态查询只返回 `{"job_id", "status": "running"}`——
**「卡死」与「只是慢」在外部无法区分**。ATP 内部有数据（`progress_cb` / `job.results` /
`scenario_entries`），暴露 progress + queue_position 即可。（ARS 的 §4.9.2 已有
`progress: {units_done, units_total}`——**参考实现不该比抄它的那个信息量少**。）

## 8. 明确不做（避免反复重开）

| 项 | 理由 |
|---|---|
| tzcomm 走 ATP 评测通路 | **循环依赖**：ATP 基于 tzcomm，六个核心模块 import 它，`/atp/health` 直报 `"tzcomm": true`——tzcomm 真出问题时 ATP 自己起不来。且 tzcomm 已有 19 个 pytest + 完整 GHA 矩阵；语义也错配（无 body / 无 observation / 无指标阈值） |
| ROS2 桥建在 ATP 内 | 归 tzcomm 生态：ATP 更轻，且所有 tzcomm 成员（算法仓、simulator）都受益。ATP 只留协议握手那 ~80 行 |
| 机械臂样例作为 slam/nav 铺垫 | 与倒立摆**结构完全同构**（空壳 body、无传感器、合成数据、现成阈值），碰不到任何真实难点。它仍有一个正当用途：**验证教程**——让另一位工程师照第 2 关独立走一遍。两个目标不要混 |
| ATP 牵头四平台协作基础设施（G1/G6/G8…） | 价值只在四方都做时兑现；契约未冻、落点未定前牵头即投机。已作为建议提交协同轨，等认领 |
| 拆 `conclusion` 为 `outcome`/`verdict` | 总契约 R13 已定：影响面覆盖四方，v1.7 不做，记为技术债 |
