# 算法测试接入手册（atp 最终形态）

> 读者：算法工程师。目标：回答一个问题——**"我要在 atp 平台上测试自己的算法，到底需要定义哪些东西？"**
>
> 本文只描述最终形态（v1.3 契约 + v1.1 插件架构冻结后的样子），不涉中间形态。
> SUT 侧协议字段级细节见 [算法接入指南.md](算法接入指南.md)（SLAM 示例），本文是算法无关的总览与定义清单。

---

## 1. 一张图看懂最终形态

```
                        ┌──────────────────────── 定义链（谁定义什么）────────────────────────┐
                        │                                                                  │
 body.yaml ──▶ plugin 包 ──▶ scenario.yaml ──▶ manifest ──▶ SUT（你的算法进程）──▶ CI workflow
 (本体资产)   (plugins/<ns>)  (评测场景)      (算法仓库根)   (4 个钩子)             (.github/workflows)
 机器人型号    数据 schema      选数据集+checker  launch       协议收发              Hub 触发+回调
 传感器布置    +checker+数据源  +传感器+超参      +consumes
                        │                                                                  │
                        └──────────────────────────────────────────────────────────────────┘

 运行期：Autotest Service（常驻）读 manifest → 装配 scenario（校验 produces⊇consumes、body 对齐）
        → 拉起你的 SUT 进程（注入 AUTOTEST_SESSION / AUTOTEST_TOPICS）
        → World 喂帧 → 你的算法回 result/action → Checker 打分 → report.json → CI 回调 Hub
```

**核心原则：算法是黑盒。** 你不感知场景、数据集、GT、checker；一切输入输出走协议（obs/result/action/ctl 四个通道）。评测内容（数据、判过标准）由 plugin + scenario 定义，与算法仓库解耦。

## 2. 先选路径

| | 路径 A：复用已有插件 | 路径 B：新算法类型自建插件 |
|---|---|---|
| 适用 | 你的算法属于已有评测类型（当前：`pipe.slam` 管道SLAM / `nav2d` 2D导航 / `ctrl.invp` 倒立摆 / `manip.force` 接触力控） | 新算法类型（如新感知类） |
| 你要定义 | manifest + SUT（+ CI） | data schema + checker + dataset + scenario + manifest + SUT（+ CI） |
| 工作量 | 半天级 | 需与评测负责人对齐 schema 与判过标准 |

**路径 A 直接跳到 §3.6（manifest）**；路径 B 从 §3 开始按顺序读。

## 3. 定义链逐环详解（路径 B 全量；路径 A 只读 §3.4–§3.6）

### 3.0 名词卡

| 名词 | 是什么 | 在哪 |
|---|---|---|
| **body** | 本体资产：机器人型号 + 传感器布置（类型→实例→topic）+ 外参 | `body/pbox_v1.yaml`（已有，通常不需新建） |
| **plugin** | 某算法类型的评测包：数据 schema + checker + 数据源 | `plugins/<命名空间>/`（如 `plugins/pipe.slam/`） |
| **scenario** | 评测场景：body + dataset + checker + 传感器/超参 | 评测仓库 YAML（如 `examples/*.scenario.yaml`、`scenarios/`） |
| **manifest** | 算法侧静态声明：launch + consumes + 建议场景 | **你的算法仓库根目录 `scenario.yaml`** |
| **SUT** | 被测算法进程（你的代码，黑盒） | 你的算法仓库 |
| **World** | 数据源抽象：数据集回放 / 仿真 / 真实设备三形态透明切换 | 框架 `autotest.world.*` |

### 3.1 body（本体资产）—— 了解即可

- 所有评测必须声明 body（`scenario.yaml` 的 `body: pbox_v1`），数据集与本体对齐校验由框架 fail fast。
- 你唯一需要关心的：body 定义了 `sensor_config`（{传感器类型: {实例名: topic}}），INIT 时下发给你；你的 `required_sensors` 声明的实例名必须被它覆盖。
- 新机器人型号才需要新建 body.yaml（找评测负责人）。

### 3.2 plugin 之一：data schema（数据格式）

**文件 `plugins/<ns>/data.py`** —— 定义三种 payload 与跨进程编解码：

| payload | 方向 | 说明 |
|---|---|---|
| observation | World→你 | 每帧观测（如 `SlamData`：多实例传感器容器 + odom） |
| result/action | 你→World | 开环回 result（如位姿），闭环回 action（如速度指令） |
| ground_truth | World→checker | GT（进程内传递、**不编码**，如轨迹/目标点/障碍） |

- 每个 schema 有命名空间键（如 `pipe.slam.SlamObs`），用 `register_data("observation"|"result", 键, 解码, 编码)` 注册；编码统一 msgpack，二进制字段（点云）走 `{shape, dtype, data:bytes}`。
- **这是路径 B 最关键的对外契约**：observation 决定你每帧收到什么，result/action 决定你要回什么。定稿前与评测负责人对齐。

### 3.3 plugin 之二：checker（判过标准）

**文件 `plugins/<ns>/checker.py`** —— 实现 `IChecker.evaluate(records, ground_truth, config) -> Score`：

- `consumes` 声明依赖的观测 schema（装配期校验 produces⊇consumes，fail fast）。
- 输入：records（开环=你的 result 列表；闭环=observation 轨迹）+ GT 信封 + 阈值配置（`checker_config`，如 `ate_threshold`）。
- 输出：`Score(metrics={...}, passed=bool)`。metrics 进报告，passed 决定 CI 红绿。
- 参考：[pipe.slam APE/RPE](../plugins/pipe.slam/checker.py)（开环）、[nav2d 到点+安全裕度](../plugins/nav2d/checker.py)（闭环）。

### 3.4 plugin 之三：dataset / world（数据来源）

三形态对算法**完全透明**（同一套协议，只是 World 不同）：

| 形态 | 注册键示例 | 用途 |
|---|---|---|
| 合成/回放 | `pipe.slam.synthetic` / `pipe.slam.rosbag` | 离线数据集逐帧喂（开环主形态） |
| 仿真闭环 | nav2d `SimWorld` | World 收你的 action 推进状态（闭环主形态） |
| 实时流/真机 | `pipe.slam.rostopic` / `pipe.slam.device` | 接 ROS topic / 真实设备 |

- 离线数据集类实现：`testcases` / `frames(testcase_id)` 逐帧产 observation 信封 / `ground_truth(testcase_id)` 产 GT 信封，并声明 `produces`。
- 闭环仿真类实现 `IWorld`：`reset/step(action)/get_ground_truth`，参考 [nav2d SimWorld](../plugins/nav2d/sim.py)。
- 注册：`register_dataset("<ns>.<名>", lambda **cfg: DatasetWorld(...))`（见 [pipe.slam/__init__.py](../plugins/pipe.slam/__init__.py)）。

### 3.5 scenario.yaml（评测场景）

```yaml
body: pbox_v1                        # 必填：本体资产
dataset:
  type: pipe.slam.synthetic          # 数据源（命名空间键）
  config: { n_testcases: 2, n_steps: 50 }
checker: pipe.slam.ape               # 判过（空 = 只验证数据流）
checker_config: { ate_threshold: 0.2 }
sensor_config:                       # INIT 下发给算法（实例名须与观测一致）
  lidar: { front: /rslidar_points_front }
hyperparams: {}                      # 算法超参，INIT 下发
```

装配期三重校验（fail fast，错误信息明确）：body 对齐 / produces⊇consumes / 注册键存在。

### 3.6 manifest（算法仓库根目录 `scenario.yaml`）★ 你必写

```yaml
launch: "python3 main.py"            # 启动命令（相对本文件目录执行）
consumes: ["pipe.slam.SlamObs"]      # 你消费的 observation schema（须与插件一致）
scenario: scenarios/synthetic_slam.yaml   # 建议场景（评测方可 --scenario 覆盖）
required_sensors:                    # 所需传感器实例（握手时按 body 校验）
  lidar: [front]
hyperparams: {}                      # 超参（与场景合并后 INIT 下发）
# image: "registry/algo:v1"          # 可选：填了则 docker+bind 拉起（--network host）
```

模板：[examples/slam_algo.scenario.yaml](../examples/slam_algo.scenario.yaml)。

### 3.7 SUT（算法进程）★ 你必写

用 SDK（`autotest.sdk.SutBase`）只需覆写 **4 个钩子**：

```python
class MyAlgo(SutBase):
    module = "pipe.slam"              # 命名空间

    def on_init(self, config): ...    # 收 sensor_config+hyperparams → 回能力宣告
    def on_reset(self, meta): ...     # 每个 testcase 前：清状态、保模型
    def on_step(self, observation):   # 每帧：解码→推理→回 Result(开环)/Action(闭环)
        data = decode_observation(observation["data"])
        return msg.Result(self.module, encode_result("pipe.slam.StampedPose", out))
    def on_terminate(self, reason):   # 收尾：可回自统计 dict（进报告）
        return {}
```

- 会话身份（`AUTOTEST_SESSION`/`AUTOTEST_TOPICS`）由 Service 注入，SDK 自处理；**话题名不硬编码**。
- **时钟以 STEP 的 `timestamp` 为准**，禁读墙上时钟（Service 可加速回放）。
- reset 语义：同实例跨 testcase 复用，**清运行状态、保留模型/参数**。
- 参考实现：[examples/slam_algo.py](../examples/slam_algo.py)（开环）、[examples/invp_sut.py](../examples/invp_sut.py)（闭环·最简 PD 样例）、[examples/nav_sut.py](../examples/nav_sut.py)（闭环·导航）；ROS2 算法经 [ros2_pipe_bridge.py](../examples/ros2_pipe_bridge.py) 桥接。
- 协议字段级细节（消息类型/时序/数据格式）：[算法接入指南.md](算法接入指南.md) §5–§6。

### 3.8 CI（.github/workflows/autotest.yml）

拷贝 [examples/ci/autotest.yml](../examples/ci/autotest.yml) 到算法仓库即可，零改动：

- 仅 `workflow_dispatch`（Hub 触发，带 correlation_id/commit）；runner 上 `client run --json` 评测，末步回调 Hub（Bearer 鉴权 + 实际 sha + conclusion + 摘要）。
- **回归基线（M-D3）**：评测后自动执行 `client report <job_id> --json` 与 Service 产物目录中的 `baseline.json` 对比，回调摘要携带 `vs_baseline` 变化计数（regressed=回归，需关注）；Hub 触发时置 `save_baseline=true`（主干/发版评测）则先对比、后把本次结果滚为新基线。
- 前置：仓库配 `HUB_CALLBACK_TOKEN`(secret) / `HUB_CALLBACK_URL`+`AUTOTEST_ARTIFACTS_DIR`(变量，后者=评测机 Service 产物目录)；self-hosted runner 能连 Autotest Service 与 tzcomm daemon。

## 4. 运行与调试归因

### 4.1 本地跑一次

```bash
python3 -m autotest.client run <算法仓库>/scenario.yaml [--scenario 覆盖场景] [--clock-rate 1.0] [--json]
```

> 环境前提：tzcomm daemon 与 autotest server 已启动；未 pip 安装时用 `PYTHONPATH=<atp仓库绝对路径>/src`
> （**必须绝对路径**——SUT 子进程工作目录会切到 manifest 所在目录，相对路径会导致子进程 import 失败）。

### 4.2 暂停/单步（调试算法时）

评测跑到一半想看算法现场（attach 调试器、打印中间量）？`run` 是阻塞等待的，**另开一个终端**对运行中的 job 发调试命令：

```bash
python3 -m autotest.client pause <job_id>        # 世界冻结：停喂帧，SUT 安全等待
python3 -m autotest.client step <job_id> -n 10   # 暂停中单步放行 10 帧（默认 1）
python3 -m autotest.client resume <job_id>       # 恢复全速
```

- `job_id` 见 `run` 提交后的 stderr 输出；进度经 `job/status` 可查 `run_state`（running/paused）与 `frames`（已放行帧数）。
- 暂停语义：World 停喂帧、时钟冻结，SUT 阻塞等下一帧——观察/断点的安全态，不会因超时被框架判死。
- `step` 仅在暂停中有效（非暂停发 step 报错）；`resume` 后残余配额作废，不会多走"幽灵帧"。
- 开环（数据集回放）与闭环（仿真）同样适用；闭环暂停时仿真随之停步（每帧由 action 驱动）。

### 4.3 链路预检（怀疑 tzcomm 时先跑）

```bash
python3 -m autotest.commcheck          # daemon 可达 / SUBPUB 回环 / Service 回环，退出码 0/1
```

### 4.4 归因速查（框架 vs tzcomm vs 算法）

| 症状 | 看哪里 | 归因 |
|---|---|---|
| `report.json` 的 `comm_health.warnings` 非空 | Service/SUT 双侧丢包率超 1% | **tzcomm 链路**（丢包），把报告发给 tzcomm 负责人 |
| SUT 进程未拉起 / 无 ready | server 日志 launch 报错 | manifest `launch` 或环境（`PYTHONPATH`/docker） |
| 装配期 fail fast | 报错直指缺失项 | scenario/manifest 声明不一致（schema 键、传感器实例名、body） |
| 收不到帧 / 卡 step | `TZCOMM_LOG_LEVEL=DEBUG` 起 SUT（SDK 自动开 tzcomm 日志） | 发现层/话题名 |
| metrics 异常但链路正常 | checker 的 metrics 与 GT | **算法本身** |
