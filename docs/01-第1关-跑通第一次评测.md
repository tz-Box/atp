# 第 1 关：跑通第一次评测

> **学习目标**：亲眼看完一次评测的全过程，认出[导读](00-导读与学习路径.md)里那四个问题分别由哪个文件回答，并能逐字段读懂报告。
> **本关不需要理解**：通信协议、插件内部实现、CI——那是第 2、4、5 关的事。
> **用时**：30 分钟。**角色**：算法工程师和测试工程师都读。

---

## 1.1 三十秒认识被测对象：倒立摆

我们用团队现成的算例仓 `cicd_test` 当教具。它测的是一个经典控制问题：

```
                    ┃  ← 摆杆（长 1 m，质心在中点）
                    ┃      θ = 摆杆与竖直方向的夹角，θ=0 即立直
                    ●
            ┌───────┴───────┐
      ←── F │     小车       │ ──→        x = 小车在轨道上的位置
            └──○─────────○──┘
    ════════════════════════════════════  轨道（半宽 2.4 m）
```

- 每 20 ms（50 Hz），世界告诉算法四个数：小车位置 `x`、小车速度 `x_dot`、摆角 `theta`、摆角速度 `theta_dot`。
- 算法回一个数：施加在小车上的水平力 `force`（会被截断到 ±10 N）。
- 世界拿这个力积分一步物理，产生下一帧观测。**这就是闭环**——你的输出决定了你的下一个输入。
- 三种结局：摆角超过 ±0.2095 rad（≈12°）判 `fell`；小车出轨判 `out_of_bounds`；撑满 500 步（10 秒）判 `survived`。

**及格线**：撑满 10 秒不倒（`survived`），**并且**最后 10% 时间里平均 |θ| ≤ 0.02 rad。
被测算法是一个 PD 状态反馈控制器：`F = kp·θ + kd·θ̇ + kx·x + kxd·ẋ`
（[`invp_sut.py`](https://github.com/tz-Box/cicd_test/blob/main/invp_sut.py)，全文 40 行）。

## 1.2 跑一次

本关的教具是团队的算例仓 [`tz-Box/cicd_test`](https://github.com/tz-Box/cicd_test)。先克隆一份到本地
（评测机上通常已经有了，`CICD_TEST` 指向它即可）：

```bash
git clone git@github.com:tz-Box/cicd_test.git ~/ws/cicd_test
export CICD_TEST=~/ws/cicd_test        # 本关后面都用这个变量指代它
```

然后跑一次评测：

```bash
python3 -m autotest.client run "$CICD_TEST/scenario.yaml" --json
```

真实输出（为便于阅读做了换行，实际是单行 JSON）：

```
job_id: autotest-d9b59415（调试：python3 -m autotest.client pause/step/resume <job_id>）
{"ok": true, "job_id": "autotest-d9b59415", "results": [
  {"testcase_id": "small_push:small_push",
   "metrics": {"survived": 1.0, "survival_time": 10.0, "max_abs_theta": 0.05,
               "settle_error": 3.9e-05, "upright_ratio": 1.0},
   "passed": true, "n_records": 501},
  {"testcase_id": "full:small_push",  "metrics": {...同上...}, "passed": true, "n_records": 501},
  {"testcase_id": "full:medium_push",
   "metrics": {"survived": 1.0, "survival_time": 10.0, "max_abs_theta": 0.103036,
               "settle_error": 0.000133, "upright_ratio": 1.0},
   "passed": true, "n_records": 501}],
 "comm_health": {"service": {"msgs": 1000, "lost": 0, "loss_rate": 0.0},
                 "sut": {"msgs": 1000, "lost": 0, "loss_rate": 0.0}, "warnings": []}}
```

刚才那一条命令背后发生了什么（**现在只需要有个印象**，第 2 关讲细节）：

```
你的命令 ──▶ ATP 服务（常驻进程）
                │
                ├─① 读 cicd_test/scenario.yaml，知道怎么启动算法、要跑哪几个场景
                ├─② 按场景把仿真世界装配起来（倒立摆动力学 + 判据）
                ├─③ 用 launch 命令把你的算法拉起来，成为一个独立进程
                ├─④ 握手：告诉算法"会话开始了，这是你的超参"
                ├─⑤ 逐 testcase：重置世界 → 循环（喂观测 → 收指令 → 推进物理）
                ├─⑥ 每个 testcase 跑完，把整条轨迹交给判据打分
                └─⑦ 汇总成报告，落盘到 artifacts/<job_id>/
```

## 1.3 逐字段读报告

| 字段 | 含义 | 这次的值说明什么 |
|---|---|---|
| `job_id` | 这次评测的编号，全链路追踪锚点 | 现场在 `artifacts/autotest-d9b59415/` |
| `testcase_id` | 一个具体工况的编号 | 见下方"前缀规则" |
| `metrics` | 判据算出的**全部指标**，进报告供人分析 | 见 §1.4 |
| `passed` | 这个 testcase 过没过，**红绿由它决定** | 三条全 `true` |
| `n_records` | 判据收到多少条记录 | `501` = 1 条 reset 首帧观测 + 500 步 |
| `comm_health` | 底层通信健康度，**服务端和算法端各自统计** | 双侧 1000 条零丢包。这不是算法指标，是链路自检 |

**testcase_id 的前缀规则**：`cicd_test` 的 manifest 声明了两个场景（`small_push` 和 `full`），这次没指定跑哪个，所以两个都跑了。**当一次评测跑多于一个场景时，testcase_id 会带上 `场景id:` 前缀**；只跑一个场景时没有前缀。所以：

- `small_push:small_push` = `small_push` 场景里的 `small_push` 工况
- `full:small_push` / `full:medium_push` = `full` 场景里的两个工况

（`full` 场景包含 `small_push` 工况，和第一个场景重复了——这是算例仓有意为之：PR 时只跑 smoke，主干跑全量，重复的工况保证两级之间可比。第 3 关会讲这种分级设计。）

## 1.4 五个 metric 分别在说什么

| metric | 这次的值 | 含义 | 类型 |
|---|---|---|---|
| `survived` | 1.0 | 撑满 500 步了吗（1=是） | **结论型**，参与 passed 判定 |
| `settle_error` | 3.9e-05 | 末段 10% 时间的平均 \|θ\|，即稳态残余摆角 | **结论型**，参与 passed 判定 |
| `survival_time` | 10.0 | 撑了多少秒 | 诊断型：没过时告诉你"撑到第几秒倒的" |
| `max_abs_theta` | 0.05 | 全程最大 \|θ\| | 诊断型：离 0.2095 的失败线还有多少余量 |
| `upright_ratio` | 1.0 | 有多大比例的帧摆是立着的 | 诊断型 |

**`passed` = `survived` 且 `settle_error ≤ 0.02`**——只有两个结论型指标参与判定，其余三个纯粹是给人看的诊断信息。

这个"结论型 / 诊断型"的区分很重要：**passed 必须单一、明确、不可争辩；metrics 要尽可能丰富，让人一眼看出为什么没过**。第 3 关设计自己的判据时会用到。

注意 `full:medium_push` 的 `max_abs_theta = 0.103`——初始扰动就是 0.10 rad，说明这个 PD 控制器一次都没让摆角超过初始值，从第一步就在往回收。这就是诊断型指标的价值：`passed: true` 只告诉你过了，`max_abs_theta` 告诉你**过得有多轻松**。

## 1.5 认出四个角色

现在把这次评测拆开，对照[导读](00-导读与学习路径.md)的四个问题：

| 问题 | 这次由谁回答 | 文件 | 内容 |
|---|---|---|---|
| **Q1 考谁** | PD 控制器进程 | [`cicd_test/invp_sut.py`](https://github.com/tz-Box/cicd_test/blob/main/invp_sut.py) | 40 行，收 4 个数回 1 个数 |
| **Q2 怎么考** | 倒立摆仿真世界 | [`plugins/ctrl.invp/sim.py`](../plugins/ctrl.invp/sim.py) | 车-摆动力学，半隐式欧拉积分 |
| **Q3 考什么** | 两档初始扰动 | [`cicd_test/scenarios/sim_basic.yaml`](https://github.com/tz-Box/cicd_test/blob/main/scenarios/sim_basic.yaml) | `small_push: theta0=0.05` / `medium_push: theta0=0.10, theta_dot0=0.2` |
| **Q4 算不算过** | 存活 + 稳态误差判据 | [`plugins/ctrl.invp/checker.py`](../plugins/ctrl.invp/checker.py) + 场景里的 `settle_threshold: 0.02` | 判据实现在 ATP 仓，阈值在你的仓 |

把场景文件打开看一眼，它短到可以全文贴在这里：

```yaml
# cicd_test/scenarios/sim_basic.yaml
body: invp_sim                      # Q2 的一部分：用哪个本体（这里是纯仿真台架，无传感器）
dataset:
  type: ctrl.invp.sim               # Q2：用哪个世界——倒立摆仿真
  config:
    testcases:                      # Q3：考哪些工况
      small_push:  { theta0: 0.05 }
      medium_push: { theta0: 0.10, theta_dot0: 0.2 }
checker: ctrl.invp.upright          # Q4：用哪把尺子
checker_config: { settle_threshold: 0.02 }   # Q4：尺子上的刻度
```

**这 9 行就是一个 benchmark 的完整定义。** 第 3 关整关都在讲怎么把这 9 行写好。

再看 manifest（仓根的 `scenario.yaml`，回答 Q1 + 组织场景清单）：

```yaml
# cicd_test/scenario.yaml
launch: "python3 invp_sut.py"        # Q1：怎么把你的算法启动起来
consumes: ["ctrl.invp.InvpObs"]      # Q1：我这个算法吃的是"倒立摆观测"这种数据
required_sensors: {}                 # 纯仿真，不需要任何传感器
hyperparams: {}                      # 算法超参默认值（PD 增益在算法里有内置默认）
scenarios:                           # 这个仓提供哪几套题
  - id: small_push
    description: 小扰动单点冒烟（PR 快速反馈）
    scenario: scenarios/small_push.yaml
  - id: full
    description: 完整评测（小 + 中扰动两用例）
    scenario: scenarios/sim_basic.yaml
```

> **两个 `scenario.yaml` 别搞混**：仓根那个叫 **manifest**（"这个仓怎么被测"），`scenarios/` 目录下那些叫**场景文件**（"一次评测跑什么数据、用什么判定"）。报错信息里说 manifest 时，指的一定是仓根那个。

## 1.6 一个 testcase 内部的时序

这张图第 2 关会反复用到，现在扫一眼建立印象即可：

```
ATP 服务                                            你的算法进程
   │                                                     │
   │──── INIT（超参、传感器配置）────────────────────────▶│  进程刚被拉起
   │◀─── READY（我是谁、我需要什么传感器）────────────────│
   │                                                     │
   │  ┌── testcase: small_push ──────────────────────────────────────┐
   │  │                                                     │        │
   │  │─ RESET（testcase_id）──────────────────────────────▶│ 清运行状态
   │  │◀ RESET_ACK ─────────────────────────────────────────│ （但保留模型/权重）
   │  │                                                     │        │
   │  │  世界 reset → 首帧观测 (x=0, θ=0.05, ...)           │        │
   │  │─ STEP（观测）──────────────────────────────────────▶│        │
   │  │◀ ACTION（force=1.53）───────────────────────────────│  ← 你的控制律
   │  │  世界按 force 积分 dt=0.02s，产生下一帧              │        │
   │  │─ STEP（观测）──────────────────────────────────────▶│        │
   │  │◀ ACTION ────────────────────────────────────────────│        │
   │  │            ……重复 500 次或直到摔倒……                │        │
   │  │                                                     │        │
   │  │  整条观测轨迹 + 真值 → Checker → Score(metrics, passed)      │
   │  └──────────────────────────────────────────────────────────────┘
   │        （下一个 testcase 从 RESET 再来一遍，进程不重启）
   │                                                     │
   │──── TERMINATE ─────────────────────────────────────▶│
   │◀─── FINAL（算法侧自统计）───────────────────────────│  进程退出
```

三个要点先记住：

1. **INIT 只发一次，RESET 每个 testcase 一次**。RESET 的语义是"**清运行状态、保留模型和参数**"——同一个算法进程要跨 testcase 复用，不能有状态残留。
2. **闭环模式下算法回 ACTION**（控制量）。开环模式（SLAM 这类）回的是 RESULT（估计量），世界不受影响，其余流程完全一样。
3. **判据在整个 testcase 跑完之后才介入**，一次性拿到整条轨迹打分。算法全程不知道判据的存在。

## 1.7 动手：让它变红

这是本关最重要的一步。**判据没变、世界没变，只把算法调差**，看报告怎么反应。

新建一个临时目录当"算法仓"：

```bash
mkdir -p /tmp/invp_demo/scenarios
cp "$CICD_TEST/invp_sut.py" /tmp/invp_demo/

cat > /tmp/invp_demo/scenarios/hard_push.yaml <<'EOF'
body: invp_sim
dataset:
  type: ctrl.invp.sim
  config:
    testcases:
      hard_push: { theta0: 0.18, theta_dot0: 0.8 }   # 大初始摆角 + 快速倒下的初速度
checker: ctrl.invp.upright
checker_config: { settle_threshold: 0.02 }
EOF

cat > /tmp/invp_demo/scenario.yaml <<'EOF'
launch: "python3 invp_sut.py"
consumes: ["ctrl.invp.InvpObs"]
required_sensors: {}
hyperparams: {}
scenarios:
  - id: weak_gain
    description: 低增益 + 大扰动（预期失败）
    scenario: scenarios/hard_push.yaml
    hyperparams: { kp: 8.0, kd: 1.0 }      # 算法默认 kp=30, kd=5，这里调到远远不够
EOF

python3 -m autotest.client run /tmp/invp_demo/scenario.yaml --json
```

真实输出：

```json
{"ok": true, "job_id": "autotest-7195bdf2", "results": [
  {"testcase_id": "hard_push",
   "metrics": {"survived": 0.0, "survival_time": 0.04, "max_abs_theta": 0.211496,
               "settle_error": 0.211496, "upright_ratio": 0.6667},
   "passed": false, "n_records": 3}]}
```

**读这份失败报告**：

- `passed: false`——CI 会变红。
- `survived: 0.0` + `survival_time: 0.04`——只撑了 40 毫秒，也就是**两步就倒了**。
- `max_abs_theta: 0.211496` 刚刚越过失败线 0.2095——确实是"摔倒"终止的，不是出轨。
- `n_records: 3` = 1 帧 reset 观测 + 2 步。跟 `survival_time / dt = 0.04 / 0.02 = 2` 对得上。
- `testcase_id` 没有前缀——因为这次只跑了一个场景（印证 §1.3 的前缀规则）。

**请注意刚才发生了什么，这是整套框架的价值所在**：

> 你**没有碰**判据（`checker.py` 在 ATP 仓，你根本改不到）；
> 你**没有碰**世界（仿真动力学也在 ATP 仓）；
> 你只是把算法的增益改差了，报告立刻从绿变红，而且指标精确告诉你差在哪、差多少。
>
> 这就是[导读](00-导读与学习路径.md) §4 那条黄金纪律的物理实现：**测不过时你改不到判据，只能去改算法。**

顺手做个对比实验，把 `hyperparams` 改成 `{ kp: 30.0, kd: 5.0 }`（算法默认值）再跑一次，看同样的大扰动工况能不能救回来。

## 1.8 现场在哪

每次评测都在评测机的 `artifacts/<job_id>/` 留两份现场：

```bash
cat artifacts/autotest-7195bdf2/session.log
```

```
[17:27:59] 场景[weak_gain]: manifest=/tmp/invp_demo body=invp_sim dataset=ctrl.invp.sim
[17:27:59] 数据源: ctrl.invp.sim testcases=['hard_push'] checker=ctrl.invp.upright body=invp_sim
[17:27:59] testcase hard_push: passed=False metrics={'survived': 0.0, ...} records=3
```

| 文件 | 内容 | 什么时候看 |
|---|---|---|
| `report.json` | 完整报告：manifest 摘要、场景清单、逐 testcase 结果、通信健康 | 要机读结果、要做回归对比时 |
| `session.log` | 执行流水：装配了什么、算法进程有没有起来、每个 testcase 什么结论 | **出问题第一时间看这个** |

排障时的第一反射：**先看 `session.log`**。它按时间顺序告诉你评测走到哪一步、在哪一步崩的。
