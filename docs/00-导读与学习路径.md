# 导读：这套框架解决什么问题

> 读者：第一次接触 ATP 的**算法工程师**与**测试工程师**。
> 读完本文你不会写任何代码，但会拿到一张地图：知道自己要学什么、按什么顺序学、学到哪里算够用。
> 用时 15 分钟。

---

## 1. 先说问题：机器人算法为什么难测

你写完一个新算法——姿态控制器、SLAM、抓取规划。怎么证明它"行"？

现实中大家的做法通常是这三种，各有各的天花板：

| 做法 | 天花板 |
|---|---|
| 手动跑一遍，看曲线、看 rviz | 不可复现、不可比较、换个人复核结论就变；改一行代码不知道有没有变差 |
| 写单元测试 | 测得了"这个函数返回值对不对"，测不了"在 200 种工况下摆能不能立住" |
| 攒一堆一次性脚本 | 每个算法一套、每个人一套；脚本本身没人评审，判据藏在某人的 numpy 里 |

难点在于机器人算法的两个特性：

1. **输入是时序的、有物理因果的**——不是一批独立样本，是一条有先后关系的轨迹；
2. **闭环时输入取决于你自己的输出**——控制器这一步施加的力，决定了下一步收到的观测。这意味着"喂一份数据集"根本测不了控制器，你必须给它一个**会回应它的世界**。

所以机器人算法测试的最小单位不是"一个断言"，而是**一次受控的、可复现的交互过程**。

## 2. 这套框架的一句话定位

**把机器人算法测试做成 OJ（在线判题）。**

| OJ 概念 | 这里对应 |
|---|---|
| 提交的程序（黑盒） | 你的算法进程（SUT） |
| 题目的输入数据 | 数据集回放 / 仿真世界 / 真机数据流（World） |
| 标准答案 + 评分脚本 | 判据（Checker）+ 真值（Ground Truth） |
| 判题结果（AC/WA + 用时） | 评测报告（passed + metrics） |
| 题库与题目分级 | 场景清单（smoke / full / 边界 / 扰动） |

和普通 OJ 的差别只有一条，但很关键：**题目的输入是时序的，闭环时还会回应你的输出**。这条差别就是 World 这个抽象存在的全部理由。

**核心设计原则（贯穿全套框架，请记住）：算法是黑盒。**
你的算法不知道自己在被谁测、用什么数据测、及格线是多少。它只做一件事：**收观测，回结果**。
因此同一份算法代码，接仿真、接数据集、接真机，**一行不用改**。

## 3. 一次完整的测试 = 回答四个问题

这是整套教程的骨架。后面每一关，就是学会回答其中一个问题。

| # | 问题 | 术语 | 主要由谁回答 | 落在哪个文件 |
|---|---|---|---|---|
| **Q1** | **考谁？** | SUT（被测算法进程） | 算法工程师 | 你的算法仓：算法进程 + 仓根 `scenario.yaml` |
| **Q2** | **怎么考？** | World（测试方式） | 算法 + 测试工程师共建 | ATP 仓 `plugins/<命名空间>/sim.py` 或 `dataset.py` |
| **Q3** | **考什么？** | testcase / 场景 | 测试工程师 | 你的算法仓 `scenarios/*.yaml` |
| **Q4** | **算不算过？** | Checker + 阈值 + 基线 | 测试工程师 | ATP 仓 `plugins/<命名空间>/checker.py` + 场景里的 `checker_config` |

注意 Q2 和 Q4 落在 **ATP 仓**，Q1 和 Q3 落在**你的算法仓**。这个分工不是随意的：

- Q2/Q4 是"这**一类**算法该怎么被考"——是**考纲**，要被多个算法仓共用，必须有唯一权威版本，改动要评审。它们打包成一个**插件（plugin）**。
- Q1/Q3 是"**我这个**算法怎么被启动、要跑哪几套题"——跟着算法代码走，同仓评审、同版本演进。

> **一句话记住插件是什么**：插件 = 把"这类算法该怎么被考"从算法仓里独立出来，让所有同类算法用同一把尺子。

## 4. 两个角色，分开的理由

现实中常常是同一个人干两份活，但**心智上必须分开**，否则测试会失去意义。

| | 算法工程师 | 测试工程师 |
|---|---|---|
| 关心的问题 | 我的算法在这些工况下表现如何？哪里还差？ | 这类算法应该被怎么考？及格线画在哪？ |
| 产出 | 算法进程（SUT）+ 仓根 manifest | 场景文件 + 判据阈值 + 基线策略（+ checker 实现） |
| 改动频率 | 每次提交 | 版本级，改动要留记录 |
| 判断标准 | 报告变绿了吗？指标变好了吗？ | 这套题能不能区分好算法和坏算法？ |

**两条黄金纪律：**

- 算法工程师：**测不过时不许去改判据**。判据变了，历史结果就全部作废。
- 测试工程师：**算法改了不许顺手改考纲**。考纲要独立于任何一个具体算法版本，否则它衡量不了进步。

框架用文件位置把这条纪律固化下来了：判据在 ATP 仓，算法在你的仓，**你改不到它**。

## 5. 三个平台，各管一段

真正跑测试的只有 ATP 一个。另外两个平台解决的是"什么时候该跑"和"结果给谁看"。

```
   你 push 代码
        │
        ▼
    GitHub ──webhook──▶  Hub（cicd-hub）──HTTP──▶  ATP（跑测试的那台机器）
        ▲                    │    ▲                      │
        └── check-run 红绿 ───┘    └──── 评测完成回调 ─────┘
                             │
                             ▼
                        PMS（任务卡：结果落到人和任务上）
```

| 平台 | 一句话职责 | 你什么时候会碰它 |
|---|---|---|
| **ATP**（本仓） | 在评测机上真正跑测试：拉起你的算法、喂数据、打分、出报告 | 天天。第 1–4 关全在这里 |
| **Hub**（cicd-hub） | 决定"什么时候该跑一次评测"，把结果贴回 GitHub PR | 第 5 关；日常只在它页面上勾选场景 |
| **PMS** | 把评测结果贴回"人和任务"，发飞书通知 | 第 5 关；日常在任务卡上看结果 |

**一个关键设计要理解**（第 5 关展开）：Hub **不传递评测逻辑，只传递坐标**（哪个仓、哪个分支、跑哪几个场景 id）。评测该怎么做，全部来自你仓库里的文件。这跟 GitHub Actions 一个道理：`workflow.yaml` 在你仓里，runner 只是执行器。

## 7. 你属于哪条路

```
                    平台已经有你这类算法的插件了吗？
                    （现有：pipe.slam 管道SLAM / nav2d 2D导航
                          / ctrl.invp 倒立摆 / manip.force 接触力控）
                              │
              ┌───────────────┴───────────────┐
             是                               否
              │                               │
         路径 A（半天）                   路径 B（数天）
      第1关 → 2 → 3 → 5              第1关 → 2 → 3 → 4 → 5
```

**路径 B 的人请注意**：你的直觉可能是"我的算法平台没有，前三关跟我无关，直接跳到第 4 关"。**不要跳。**
第 1–3 关用倒立摆当练手材料，总共一个小时，但它让你在动手设计自己的插件之前，先完整体验过一遍"被考"的全过程。没有这个体感，你设计出来的 schema 和判据大概率要返工。倒立摆是全仓最简单的一个完整插件（约 200 行），它是你写自己插件时的模板。

## 8. 环境准备（现在就做，五分钟）

后面每一关都要用到，先确认这三件事都是通的：

```bash
# 1) 包能导入（tzcomm = 底层通信库；autotest = 本框架）
python3 -c "import autotest, tzcomm; print('ok')"

# 2) 评测服务在跑（评测机上常驻，systemd 管理）
systemctl --user is-active autotest      # 期望输出 active
curl -s localhost:2335/atp/health        # 期望 {"ok":true,"version":...,"tzcomm":true,"queue":0}

# 3) 通信链路自检（怀疑底层通信时随时可跑）
python3 -m autotest.commcheck            # 退出码 0 = 通
```

没装过的话：在 ATP 仓根 `pip install --user -e .`；服务部署见 `deploy/autotest.service` 头部注释。
任一步不通，先找评测负责人，不要带着坏环境往下走。
